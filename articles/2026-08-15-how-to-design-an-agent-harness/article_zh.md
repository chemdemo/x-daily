# 如何设计 Agent Harness：六个决策，把模型变成可以放手不管的干活的人

- **作者：** Yarchi (@undefinedKi)
- **来源：** https://x.com/undefinedKi/article/2088611136027361368
- **发布：** 2026-08-15（更新于 2026-08-15）
- **归档：** 2026-09-08（原文逐字 + 图片）

![Cover image for How to Design an Agent Harness: six decisions that turn a model into a worker you can leave alone](./media/01-cover.jpg)

你的 agent 说活干完了，测试却从没跑过。它前二十分钟很机灵，然后就忘了你一开始给过的规则。每个会话你都把同样的三条指令再打一遍。你没法走开，因为总有下一次审批在等你点。

换更好的模型解决不了这些。这一切都活在模型外面那层软件里：它被告知什么、它保留什么、它被允许碰什么、以及谁来验收结果。那层包装就是 harness。你其实已经有一个了。唯一的问题是：有没有人设计过它。

## 什么是 Agent Harness

模型和工作之间，夹着六样东西：

让它继续跑的 loop、它能调用的工具、哪些东西留在记忆里、崩溃后什么还能活下来、它被允许碰什么，以及谁判定任务完成。

其中一半是开箱自带的。厂商做了 loop、内置工具和记忆处理，你改不了多少。另一半是你的：你的指令文件、你的测试、你的权限、你对「完成」的定义。不管你有没有想过，那一半都存在。你反复往聊天里重打的每条规则，都是它的一部分。

人们从 2026 年初开始把这一层叫做「harness」。在那之前它没有公认的名字，这也是它长期无人管理的主要原因。

## 真实用例

DoorDash 把自己的做成了平台。每个 agent 跑在自己的一次性虚拟机里，启动时仓库、工具和凭证已经就位。工作本身写成 YAML playbook，把 agent 步骤和普通脚本步骤混在一起。凡是要碰到内部系统的，都走同一个网关：只下发 playbook 声明过的工具，并记录每一次调用。他们单月跑了 13 万次自动化任务，其中每周代码审查就超过 2.5 万次。

OpenAI 把自己的做成了仓库。根本没有平台。他们把仓库本身当作 harness：指令文件压到大约 100 行，当作指向真正 docs 目录的目录表；架构规则用自定义 linter 强制执行，而不是写成模型可以跳过的散文。三名工程师用这种方式在五个月内合并了大约 1,500 个 pull request。

Anthropic 把自己的做成了角色拆分。三个职责不同的 agent。一个把一句话变成规格说明。一个负责实现。一个在浏览器里驱动成品应用并打分。它们只靠互相写文件沟通。这套能跑通，代价是 6 小时、200 美元；而没有 harness 的那次跑 20 分钟、9 美元。贵了二十多倍，结果也好得多——没人会把这笔账写进广告。

三种完全不同的形态。共同点是：没有一样是开箱自带的。

## 六个决策

这才是真正划算的部分。每一条都很短：它是什么、具体怎么做、值不值、以及什么时候可以跳过。

### 1. Loop，以及它在哪里停

你的 harness 把任务加上迄今为止发生的一切发给模型。模型要么回复「请跑某个工具」，要么给出最终消息。如果是工具请求，harness 执行它，把结果粘到历史里，再整包发回去。重复，直到模型不再要工具。这就是市场上每一款产品里的完整 loop。

厂商拥有那个内层 loop。属于你的是它周围的一切：停下来之后怎么办，以及要不要再启动。

这样做：

1. 开始之前，用一句话写清你的停止规则。「完成 = 测试套件通过且应用能启动。」不是「完成 = agent 说它完成了」——那正是你现在默认拥有的东西。

2. 决定坏结局时怎么办。半路停下的一次运行，要么带着失败说明重启，要么冻结等你。二选一。没有答案，就等于 agent 默默发明自己的答案。

3. 设硬上限。轮数，或挂钟分钟数。同一个文件已经试了四十遍的 agent，第四十一遍也修不好，但它会很开心地继续花你的钱试下去。

4. 如果无人值守地跑，把每一轮都记到事后可读的文件里。你会用到它；靠记忆复原一场六小时的会话是不可能的。

有人手动梳理了五十个已公开的 agent loop。只有 74% 明确写了什么算结束，只有 32% 在多次运行之间保留任何记忆。这是清单上最便宜的修复，也是最常被跳过的那一项。

### 2. 它能看见哪些工具

模型看不见你的系统。它看见的是一份函数描述菜单，而那份菜单对它来说就是整个世界。关于这菜单，有两件事值得你留意。

这样做：

1. 别一上来就加载全部工具。如果你连了好几台 MCP 服务器，它们每一个工具描述都会在每一轮被塞进上下文，不管任务需不需要。修法是：把工具当文件放在磁盘上，让 agent 只打开它需要的那些。Anthropic 发过一个可落地的版本：从 15 万 tokens 降到 2,000。

2. 重写错误信息怎么说。多数工具失败时给的是写给人看的一句：「invalid request。」这对模型几乎等于什么都没说，于是它猜，而且通常猜错。改成返回结构：哪个字段错了、合法值长什么样、下一步试什么。Siemens 认真测过，任务完成率跳了 37 到 40 个百分点，每次成功大约只需一半 tokens。

3. 把菜单砍短。去看看你的 agent 现在能用多少工具。一个月没见它用过的，删掉。两个名字容易混淆的工具，代价比缺一个工具更大。

4. 如果自己做自定义工具，要小心：命名和分组方式会可测量地改变行为。前缀和后缀不是装饰。

如果你只在一个仓库上跑一个 agent、只用内置工具，可以跳过。省 token 是真的，但还不是你的瓶颈。

### 3. 记忆里留什么

模型关于你任务知道的一切，都活在一个缓冲区里。缓冲满了，较旧的材料会被摘要掉再扔掉。你选不了扔掉什么，模型也不会告诉你发生了这件事。

这样做：

1. 别把它填满。在百万 token 的模型上，干到 30 万或 40 万就停。再往上，失败不再像「搞糊涂了」，而像「粗心大意」——那种本该放过的配置文件被它删掉的粗心。

2. 在你选定的节点主动裁剪。别让自动压缩在任务中途开火，把工作拆成阶段：调研，然后成文文档，然后计划，然后实现。每一阶段都从一个干净窗口开始，只带上一阶段的文档。阶段之间你自己读那份文档。更慢，也可靠得多。

3. 把规则钉死。把事实和规则分开。事实可以被摘要掉。规则不行：永远别碰生产、永远别提交密钥、这份 API 契约是固定的。把这些放进 agent 每次重置后都会重读的文件，并在系统提示里再写一遍。双保险，故意的。

4. 它开始一味附和你时就重启。如果模型连续五次毫无异议地接受建议，这个会话就该结束了。早期混进了什么错误，之后的一切都会把它当既定事实。开一个新窗口。

一项研究测量了 agent 违反书面策略规则的频率：规则完整可见时违规为零；压缩之后变成 30%；最差的模型上到 59%。规则若在摘要后仍存活，违规仍为零。钉死规则彻底修好了这个问题。那篇论文是单作者且未经审稿，所以把数字当强提示，别当铁证。不管怎么说，修它只需要一个下午。

### 4. 崩溃后什么还能活下来

你的 agent 会在任务中途死掉。窗口满了、进程崩了、你合上了笔记本。只活在对话里的东西就没了。

这样做。仓库里放四个文件，并告诉 agent 保持它们最新：

1. SPEC.md。你在建什么。你来写，agent 永远不改。这能防止长跑过程中目标漂移。

2. PLAN.md。步骤，每一步都有明文验收标准。不是「改进错误处理。」而是「对 /orders 的请求若缺少 id，返回带消息的 400，且断言这一点的测试通过。」

3. PROGRESS.md。什么做完了、下一步是什么、试过什么且失败了。新开的 agent 第一个读的就是这个文件。

4. DECISIONS.md。只追加。每一个选择以及为什么。没有它，后来的会话会重新争论你两小时前已经做过的决定。

然后让 agent 在每一次有效改动后提交。小提交、有实质内容的 message。回滚变成 `git revert`，审查变成读 diff，你免费得到完整历史，而不用自己搭一套检查点系统。

如果你在做有许多独立功能的东西，再加第五个文件：一份普通 JSON 列表，每个功能标成通过或失败。这是最便宜的进度追踪器，agent 自己就能更新。

不在文件里的，就不存在。

### 5. 它被允许碰什么

跑在你笔记本上的 agent 拥有你的 SSH 密钥、VPN 会话，以及你登录过的每一个 CLI。它不必怀有恶意，事情也会搞砸。它只需要上下文里有一页被投毒的网页。

这样做：

1. 两道边界，做到操作系统层。限制它能写入哪些目录，并通过带允许域名列表的代理路由其网络访问。在 OS 层做，而不是在 agent 内部做，这样它拉起的任何子进程也被罩住。一个 shell 出脚本、脚本再 shell 出 curl 的 agent，已经逃出了应用内限制，但逃不出这一层。

2. 别再迷信审批弹窗。人们会批准其中 93%。你总会点过的提示不是安全控制，只是你给自己造的延迟。把提示留给那少数你会真的停下来想的事，其余一律用边界。

3. 如果多人用 agent 碰共享系统，在那些系统前放一个网关。它只下发任务声明需要的工具，并记录每一次调用。那份日志能让事故可调查，而不是神秘事件。

4. 永远别把长寿命凭证放进沙箱。短寿命 token，作用域绑到单次任务。只要 agent 能读到一把密钥，就假设那把密钥已经出现在某个上下文窗口里。

Anthropic 报告说，加上合格的沙箱后，内部权限提示减少了 84%。这才是真正的理由：它不只更安全，还烦人少得多，所以才会真的坚持用下去。

### 6. 谁说它完成了

写代码的那个 agent，是判断代码能不能用的最差人选。它自己给自己打分，而且打分很慷慨。

这样做：

1. 在另一个会话里审查。全新窗口，不记得自己写过这东西。同一个模型完全可以。要紧的是它不携带当初产出那个 bug 的推理过程。

2. 让它真的跑起来。Web 应用就在真实浏览器里驱动；CLI 就执行那条命令。读完 diff 宣布正确不是验证，只是对同一次猜测的第二意见。

3. 用你已经踩过的失败搭一个评测集。二三十到五十个任务起步就够。真实的，来自你仓库的，你亲眼见过 agent 搞砸的。

4. 每个任务跑三次，按最差那次评判。这比听起来重要。单次成功率 75%，意味着三次全过的概率只有 42%。Agent 是非确定性的，一次绿灯几乎说明不了什么。

5. 盯住那种自信的错误答案。典型的 agent 失败不是崩溃，而是撞上错误后，流畅地写一段为什么这无所谓。一项生产研究发现，这类问题大约 70% 是靠人眼察觉抓到的，不是任何测试。在日志里 grep 错误处理附近那种「解释腔」文字。

关于重试策略，没有公开数据。重试几次、用什么退避、到底该重试还是干净重启。人人都有看法，没人有数字。如果你发现自己调了好几天，要知道你已经走进了真正未经测绘的地带。

## 周末版

如果你只做五件事、别的都不做，就按这个顺序做这些。

1. 一份指令文件，不超过一百行。指向真正 docs 目录的目录表，不是百科全书。长指令文件会被略读，方式和长邮件一模一样。

2. 坏过两次的东西，变成 linter。不是一段客气请求的散文，而是会让构建失败的规则。见过真实失败就加一条；更好的模型让它没意义了就删掉。

3. 那四个文件。Spec、plan、progress、decisions。再加上每一次有效改动后的一次提交。

4. 钉死那些绝不能被摘要掉的规则。安全、策略、硬性上限。

5. 二十个任务，每个跑三次，按最差那次评判。

再往上的都是优化。

## 结语

你没法选择「不要 harness」。你现在就有一个。它是积累出来的：凌晨两点加上的每个 workaround、粘进配置又忘掉的每条规则、因为点一下比读一遍快而点过的每一次权限。其中的决策都做过了。只是不是你做的。

而且它不是免费的。Anthropic 自己有 harness 的那次运行，成本超过无 harness 的二十倍。开工前真正该回答的问题是：harness 在那些你根本没法交出去的工作上才赚回本；在你只想省二十分钟的工作上，永远不赚。

从停止规则和那四个文件开始。两样都只要一个下午。两样都能熬过下一次模型发布——这比这里多数东西都活得久。
