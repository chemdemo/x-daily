## 1. Harness · 十一套生产编码 harness 的源码解剖

**标题：** Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems  
**作者/来源：** Paul Barbaste, Tristan Darrigol, Germain Vu, Tom Wiltberger（Wavestone AI Lab / Inclusive Brains）· arXiv:2609.00006  
**链接：** https://arxiv.org/abs/2609.00006 · HTML：https://arxiv.org/html/2609.00006  
**时间：** 提交 2026-07-15（corpus 钉死到 2026-07 发行版）；抓取 2026-09-08

**原文关键段落**
> An agent is a model plus a harness: the runtime that couples an LLM to the world through a loop, tools, context management, safety controls, orchestration, and extension surfaces. … Two absences survive a threefold corpus expansion: across roughly four million lines of Python, TypeScript, and Rust, no agent runtime imports a general-purpose agentic framework … and none retrieves code with vector embeddings; the field runs on hand-rolled async loops and deterministic retrieval. … These threads converge on the paper's thesis: in the first half of 2026 the coding harness completed a turn from tool to platform.

**翻译**
> Agent = 模型 + harness：后者是把 LLM 接到世界的运行时——loop、工具、上下文、安全、编排与扩展面。……在约四百万行 Python/TS/Rust 里，没有任何 agent 运行时去 import 通用 agent 框架；也没有任何系统用向量检索代码；业界跑的是手写 async loop + 确定性检索。……论文论点：2026 上半年，编码 harness 完成了从「工具」到「平台」的转向。

**问题背景**  
Harness engineering 在 2026 初被命名后，缺少「对着生产源码说清楚 harness 到底是什么」的参考。现有基准只报分、概念 taxonomy 不落实现。本文补上这一缺口。

**核心论点与论证脉络**
1. 先给定义与边界：harness ≠ scaffold、≠ agentic framework、≠ eval harness、≠ orchestrator。  
2. 用七子系统解剖 11 套系统（Claude Code / Codex / Gemini CLI / Mistral Vibe / OpenHands / Aider / Mini-SWE-Agent / Hermes / Pi / OpenCode / OpenClaw）+ meta-harness Omnigent。  
3. 产出 13 条横切观察、29 个设计模式；纵向对比同一批系统一季度的源码 diff：收敛变成模仿，行为策略从 prompt 散文迁到配置。  
4. 平台化证据：SDK、marketplace、跨厂商 session importer、MDM 治理、agent-as-model gateway、meta-harness。

**方法/架构要点**
- 七子系统：Agent loop / LLM integration / Tools / Memory&context / Safety / Orchestration / Extensibility。  
- Loop 范式：迭代 action-observation（多数）、reflection-augmented（Aider）、coordinator-worker 叠加（Claude Code / Codex）。  
- 扩展面：SKILL.md 9/11 > MCP 8/11；ACP 六套并出现「harness hosting」。  
- 附 18 条设计建议 + 约 90 行最小可运行 harness scaffold。

**可落地启示**
- 先画清自己七子系统的「最小/最大」落点，别一上来堆框架。  
- 验证环、权限与可观测往往比「更聪明的 loop 拓扑」更能解释生产可靠性。  
- 行为政策尽量配置化（hooks / flags），少塞进会腐烂的超长 system prompt。

**与其他层关系**  
本文明确：harness 工程造**内环**（action–observation）；loop engineering 从外把内环叠成「自提示 / 自验证 / 再跑」；graph / orchestration 是子系统之一，不是默认上层。Omnigent 证明「编排层」可以迁到 meta-harness。

**评价/局限**  
迄今最硬的经验底座；不做排名/基准。Claude Code 源码钉的是流通快照，与 shipping binary 可能有差；SWE-Bench 分数因不可比已从表中拿掉。

## 2. Harness · 同一套词汇，三种架构中心

**标题：** DeepSeek Harness vs Claude Code vs Codex: Three Architectures for AI Agents  
**作者/来源：** Atoms.dev  
**链接：** https://atoms.dev/blog/deepseek-harness-vs-claude-code-vs-codex-architecture  
**时间：** 2026-08-28 · 抓取 2026-09-08

**原文关键段落**
> Claude Code is primarily about making one powerful agent more capable. Codex is about letting an agent operate inside a real computer environment with explicit execution boundaries. DeepSeek Harness is about making the runtime itself composable… Completed task = Model × Harness × Task … The important question is no longer only: How do we call the model? It is: How should intelligence, execution, policy, tools, context, and human control be organized around the model?

**翻译**
> Claude Code 主要是让「一个强 agent」更强；Codex 是让 agent 在真实计算机环境里行动且边界清晰；DeepSeek Harness 是让运行时本身可组合。……完成任务 = 模型 × harness × 任务。……关键问题不再只是「怎么调模型」，而是「智能、执行、策略、工具、上下文与人控」如何围着模型组织。

**问题背景**  
三家表面功能清单趋同（LLM、tools、loop、skills、subagents、permissions、sandbox），但产品手感差很多——需要按「架构中心」而不是功能表对比。

**核心论点与论证脉络**
- Agent-centric（Claude Code）：主 agent + skills/hooks/subagents。  
- Execution-centric（Codex）：sandbox「能做什么」与 approval「允许做什么」分离。  
- Runtime-centric（DeepSeek）：Everything is a plugin，连 loop 也可替换。  
- 用「谁拥有每个决策」矩阵比数 features 更有用。

**方法/架构要点**
- Hooks = 确定性控制贴在概率 agent 上。  
- Subagent 价值在隔离（结论回主上下文，而不是中间噪音）。  
- DeepSeek Cordis：Service definition → provider → consumer，工具依赖契约不依赖实现。  
- 可组合性的代价：概念面大，更适合平台团队而非「只想改仓库」的终端用户。

**可落地启示**
- 选型先问优化目标：体验与能力 / 安全自治执行 / 可替换平台。  
- 高风险动作：权限最小化 + 审批；别「给全权限再指望模型小心」。  
- 观测轨迹 ≠ 架构图：插件面板、trajectory、源码接口、文档要分证据类别读。

**与其他层关系**  
三者共享最底层 agent loop；差别在 harness 把控制放哪。DeepSeek 把 loop 本身插件化，直接碰到 loop engineering；多 agent 产品流（Atoms 式）则更靠近 graph 层的阶段编排。

**评价/局限**  
对比清晰、八月很新；文末夹带 Atoms 产品叙事，读架构表时自行打折。DeepSeek 仍是 developer preview，接口会变。

## 3. Loop · 四层叠环：从干活到改进 harness

**标题：** The Art of Loop Engineering  
**作者/来源：** Sydney Runkle · LangChain Blog  
**链接：** https://www.langchain.com/blog/the-art-of-loop-engineering  
**时间：** 约 2026-07（相关 webinar / 转载亦在七月）· 抓取 2026-09-08

**原文关键段落**
> The core agent algorithm is simple: give the LLM context and let it call tools in a loop until it's done. … But it’s far from the only loop that powers agents. … The hill climbing loop runs an analysis agent over those traces and uses the findings to rewrite the harness with improved configuration. … focus should pivot to loops 3 and 4 where value compounds by embedding agents into your ecosystem that continuously improve in response to your criteria.

**翻译**
> 核心算法很简单：给上下文，让模型在 loop 里调工具直到完成。……但驱动 agent 的远不止这一环。……爬山环用分析 agent 读生产 traces，据此改写 harness 配置。……重心应转向第 3、4 环：把 agent 嵌进生态，并按你的标准持续改进——价值在这里复利。

**问题背景**  
很多人把 loop engineering 理解成「再多跑几轮 ReAct」。本文用「叠环」说明：真正杠杆在验证、事件嵌入与对 harness 的元改进。

**核心论点与论证脉络**
| 环 | 作用 | LangChain 原语（文中） |
|---|---|---|
| 1 Agent | 工具循环直到任务结束 | `create_agent` |
| 2 Verification | 对照 rubric 打分，失败带回反馈重试 | `RubricMiddleware` |
| 3 Event-driven | cron/webhook/频道触发，嵌入真实系统 | LangSmith Deployment / Fleet |
| 4 Hill climbing | traces → 改 prompt/tool/grader | LangSmith Engine |

人在每一层都有自然卡点（敏感工具审批、品味级评审、改进上线前审）。

**方法/架构要点**  
验证可确定性也可 LLM-as-judge；事件环让 agent 成为常驻组件；爬山环的回流箭头要改到内环配置，而不只是再跑一次。

**可落地启示**
- 生产优先加第 2 环（可测停止条件），再上第 3 环嵌入日程/工单。  
- 第 4 环最值钱也最容易失控：要有人审 + 成本上限。  
- 「修这一次失败」应编码进 harness，而不是聊天里口头纠正。

**与其他层关系**  
文首直接说可靠工作需要 **fit-to-task 的 harness**；爬山环的优化对象就是 harness。相对 graph：单节点里可以是完整 agent loop；跨节点编排是另一层。

**评价/局限**  
框架干净、可执行；示例与原语偏 LangChain 栈。爬山环若缺治理，会变成自动改 prompt 的飞轮事故。

## 4. Loop · 企业向组件清单 + 人在环的债务

**标题：** What Is Loop Engineering?  
**作者/来源：** Ivan Belcic, Cole Stryker · IBM Think  
**链接：** https://www.ibm.com/think/topics/loop-engineering  
**时间：** 2026-07-17 · 抓取 2026-09-08

**原文关键段落**
> Loop engineering is the practice of designing agentic workflows, or loops, that iteratively guide AI agents toward completing user-defined goals with minimal human intervention. … Loop engineering reframes their role away from prompting AI agents toward one in which they design automated systems that prompt, check and guide agents. … A human-in-the-loop approach helps avoid … unverified code, comprehension debt, intent debt and cognitive surrender.

**翻译**
> Loop engineering 是设计 agentic 工作流（loops），迭代引导 agent 在最少人工介入下完成用户目标。……开发者角色从「给 agent 写 prompt」转为「设计会自行 prompt、检查与引导的系统」。……人在环是为了避免：未验证代码、理解债务、意图债务与认知投降。

**问题背景**  
术语热过后，企业需要可对照的组件表，以及「全自动」会欠下什么债。

**核心论点与论证脉络**
- 阶段：Goal → Action → Observation → Adjustment；目标必须可递归验证。  
- 组件：automations/scheduling、hooks、context engineering、tools、worktrees、skills、subagents、spine（持久进度）。  
- 相对 prompt engineering：单次指令 vs 自提示+自评估系统。  
- 风险框架：理解债务 / 意图债务 / 认知投降——测试全绿也可能没人懂代码、也没人记得「为什么这样设计」。

**方法/架构要点**  
Hooks 把治理从模型推理里挪出（省 token）；worktree 做并行隔离；maker/checker 分 agent；spine 用 markdown/看板扛跨轮状态。

**可落地启示**
- 停止条件写成机器可检（测试/量表），拒绝「网站快点」式目标。  
- 意图写进 `AGENTS.md` / `SKILL.md`，否则 agent 会优化错战略。  
- 并行用 worktree，合并前必须过验证或人审。

**与其他层关系**  
文中点名 harness engineering = 围绕 agent 的完整执行环境；loop 是其中的迭代引擎。Skills/subagents/hooks 同时是 harness 子系统。

**评价/局限**  
概念清晰、适合对齐领导层语言；深度实现细节弱于源码论文与 LangChain 实操文，文末有 Bob 产品导流。

## 5. Graph · 三年图编排经验：何时上图、何时退回 harness

**标题：** 3 Years of Graph Engineering with LangGraph  
**作者/来源：** Sydney Runkle, Harrison Chase · LangChain Blog  
**链接：** https://www.langchain.com/blog/3-years-of-graph-engineering-with-langgraph  
**时间：** 2026-07-22 · 抓取 2026-09-08

**原文关键段落**
> representing agentic systems as graphs … allows you … to impose your preconceptions of how the system should work into more constrained paths, not relying solely on the judgement of the LLM. … agent graphs are usually not DAGs. … loops are simple graphs. … what's changed is what you can put inside a node. … a node can be a full agent run — you're orchestrating agents, not just LLM calls. … Generic deep research … moved to a more agentic core loop.

**翻译**
> 把 agent 系统建成图，是为了把你对「系统该怎么走」的先验压成更受限的路径，而不是全靠模型临场判断。……生产 agent 图通常不是 DAG。……loop 就是简单的图。……真正变了的是节点里能放什么：节点可以是一整次 agent run——你在编排 agents，而不只是 LLM 调用。……通用深度研究后来反而退回更 agentic 的核心 loop。

**问题背景**  
「Graph engineering」在 X 上爆热。作者用三年 LangGraph 经验回应：图不是新发明，而是确定性路径与 agentic 步骤的平衡术；并且要会判断**何时不该图**。

**核心论点与论证脉络**
1. 节点 = 工作（确定性代码 / 单次 LLM / 带内部 loop 的完整 agent）；边 = 下一步（固定或条件）。  
2. 适合上图：支持分流、编码前探仓、合规审批等**可预见结构**。  
3. 不适合：开放式深度研究——过早硬编码路径会绑死；应退回 Deep Agents 一类 harness 让规划/委派在环内涌现。  
4. 动态边（`Send` / map-reduce）处理「运行时才知道扇出多少」。  
5. 新模式：编码 agent 作为大图中的一个节点（docs agent：Slack → 分类 → 多仓 agent → 合成 PR）。

**方法/架构要点**  
图 ≈ 状态机；循环是一等公民；认知架构 = prompt 域知识 + 图结构域知识。

**可落地启示**
- 先让**一个** loop/harness 可靠，再为明确交接（文件/PR/状态对象）加第二节点。  
- 节点按确定性光谱分级：固定 API / 单次模型 / 完整 agent。  
- 深度探索类任务默认别上复杂图。

**与其他层关系**  
Loop = 简单循环图；Graph = 多层 loop/agent 的显式接线；Harness（如 Deep Agents）是「不要图」时的退路。与昨日 Graph 综述论文同层，但这篇更偏工程判断。

**评价/局限**  
对炒作降温很有价值；自然导向 LangGraph。下载量等指标是厂商自述。

## 今日速览
1. **Harness 实证**：生产编码 agent 几乎全是手写 loop + 确定性检索；框架缺席本身就是信号；平台化（技能市场、meta-harness、配置化政策）是主线。  
2. **选型**：先定架构中心（单 agent 能力 / 执行边界 / 运行时可组合），再比功能表。  
3. **Loop**：优先验证环与事件嵌入；爬山环要有人审与预算。  
4. **Graph**：有稳定结构再上图；节点可放整 agent；开放研究可退回 harness。
