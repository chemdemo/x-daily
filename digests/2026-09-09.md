## 1. Harness · 故障六桶与七层：先命名，再改环境

**标题：** Harness Engineering: The Field Guide to Agents That Survive Contact With Reality  
**作者/来源：** spect (@spectnfa) · X Article  
**链接：** https://x.com/spectnfa/status/2097298431383417150  
**时间：** 发表 2026-09-08 · 仓库归档 `articles/2026-09-08-harness-engineering-the-field-guide-to-agents-that-survive-c/` · 抓取 2026-09-09

**原文关键段落**
> Your agent fails. You open the prompt and add a rule. … Three weeks later your system prompt is nine hundred words of scar tissue… Because most of those failures were never about reasoning. The prompt is the only layer you can see, so it becomes the only layer you edit. The actual defect is somewhere else: what the agent could see, what it was allowed to touch, what it remembered, what counted as finished. That layer has a name. It is the harness. … A prompt changes one run. A harness changes every run after it. … Capability without structure just fails more fluently. … The best harness is not the biggest one. It is the smallest system that reliably closes the gap between intent and evidence. Build to delete.

**翻译**
> Agent 失败了。你打开 prompt 加一条规则。……三周后 system prompt 成了九百字疤痕组织……因为多数失败根本不是推理问题。Prompt 是你唯一能看见的层，于是成了唯一被改的层。真正的缺陷在别处：它能看见什么、允许碰什么、还记得什么、什么叫做完。这一层叫 harness。……Prompt 只改这一次运行；harness 改之后每一次。……没有结构的能力，只会更流利地失败。……最好的 harness 不是最大的，而是能可靠闭合「意图→证据」缺口的最小系统。建完就要学会删。

**问题背景**  
长任务仍靠堆规则、换模型、扩上下文，却在「看错文件 / 乱调工具 / 忘决策 / 空口完成 / 越权 / 死磕重试」上反复摔倒。作者把这些归为环境缺陷，并给出可操作的诊断与分层建造顺序。

**核心论点与论证脉络**
1. **先诊断再打补丁**：几乎所有失败落入六桶——blind / clumsy / amnesiac / boastful / reckless / stubborn，分别对应缺上下文、缺工具网关、缺持久状态、缺证据、缺策略、缺分类恢复。  
2. **模型只是组件**：引擎 vs 车架；七层各自闭合一类失败。  
3. **合同 → 地图式上下文 → 工具网关 → 编译态记忆 → 环外策略 → 证据完成 → 按失败类恢复**。  
4. **可辨认运行**：trace + change receipt；失败后把教训沿「说明→清单→模板→自动检查→强制策略」下沉。  
5. **Harness 会腐烂**：旧 workaround 会卡住新能力；组件要像生产代码一样度量是否仍值回票价。Build to delete。

**方法/架构要点**
- Contract：objective / scope / constraints / acceptance / approval_required（YAML 示例）。  
- Context：PROJECT MAP + progressive disclosure，优化 signal/token 而非塞满窗口。  
- Gateway：model 提议意图 → gateway 授权 → tool 改环境 → sensor 回报；工具也有契约（preconditions / success evidence / risk class）。  
- State 四桶：facts / decisions / progress / lessons；从 transcript 编译，不靠重读对话。  
- Policy 按后果分级：只读自动 / 可逆自动但 trace / 外部效应要审批 / 不可逆硬门。  
- Verification：worker 与 verifier 目标不对称；verifier 有权拒而不修。  
- Recovery：重试必须改变至少一个相关条件；环有 attempts / wall clock / spend / destructive scope 预算。

**可落地启示**
- 下次失败先用六桶命名，再决定改哪一层——别默认加形容词到 prompt。  
- 空白的 harness spec 字段意味着「用你的凭证在即兴」；给真自治前先填合同与策略。  
- 度量用「被接受的产出 /（人审分钟 + 运行成本）」，别用 token 或尝试次数自欺。

**与其他层关系**  
本文几乎全写在 **harness 内环**；loop 以「观察→决定→行动→度量→接受/修复/升级/停止」出现，但是服务证据与恢复的。Graph/多 agent 明确列为「被观察到的失败赚来的复杂度」，开篇就警告别因为 prompt 偶尔含糊就上多 agent。

**评价/局限**  
结构极适合收藏当排障手册；与同日仓库里 Lunar @LunarResearcher 的 *Complete Guide*（2026-09-06）七层几乎平行，Field Guide 更短更「诊断优先」。偏编码/工程场景，对开放式研究类任务着墨少。

## 2. Loop × Graph · 检查条件、返回路径与爆炸半径门

**标题：** Loops and Graphs: how to stop babysitting agents and only approve the last step  
**作者/来源：** Hanako (@hanakoxbt) · X Article  
**链接：** https://x.com/hanakoxbt/article/2091515787366306154（课程入口 [agent-layers.vercel.app](https://agent-layers.vercel.app)）  
**时间：** 发表 2026-08-23 · 仓库归档 `articles/2026-08-23-loops-and-graphs-how-to-stop-babysitting-agents-and-only-app/` · 抓取 2026-09-09

**原文关键段落**
> A loop makes a unit of work correct without you. A graph decides which units exist at all. … Without something that can fail the work while you are out of the room, you do not have a loop. You have a scheduler. … The loop lives inside a node. The graph lives between them. … Almost everyone builds the correction edge and skips the learning edge. … Open the gate on blast radius, not on confidence. … Confidence is the weakest input in that decision… it is the only one the model can influence. The strong variable is what happens if the change is wrong.

**翻译**
> Loop 让一个工作单元在你不在时也正确；graph 决定到底有哪些单元。……没有东西能在你离开房间时把工作判失败，你就没有 loop，只有调度器。……Loop 住在节点里；graph 住在节点之间。……几乎所有人只建「纠错边」而跳过「学习边」。……开门看爆炸半径，别看置信度。……置信度是最弱输入——也是模型唯一能操纵的；真正强的变量是「改错了有多贵」。

**问题背景**  
人卡在逐步 babysit：要么只有 loop（单位很绿但整体形状错），要么只有图（并行产出未验证）。本文把两者的分工、边的真假、返回路径写到可操作粒度。

**核心论点与论证脉络**
1. Loop = produce / check / correct / repeat；**先写可编程判绿条件**（测试退出码、带源行、diff 只碰计划内文件），「看起来不错 / 模型自信 / 没抛错」都不是 check。  
2. Loop 天花板：无法决定单元集合、顺序与并行——形状错了调 loop 无效。  
3. Graph = nodes + edges；对每条箭头问「下一步是否真读了上一步输出？」答不出变量名就没有边，等待是浪费。  
4. 四类节点：splitter / worker / **code node** / gate；合并排序去重是代码，别塞模型。  
5. 两条返回路径：短纠错边（本轮）+ 长学习边（约束回写 splitter brief）；返回要带 UNIT/VERDICT/REASON/EVIDENCE/**SCOPE**，别整批打回毁掉已绿切片。  
6. Gate 按可逆性分车道：contained / wide / hard-to-reverse（第三车道根本不开，不是阈值调高）。

**方法/架构要点**
- Worker 隔离上下文，避免四人共享窗口变成「一份意见三个回声」。  
- 单单元纠错上限约三次；再红说明问题在 plan，loop 看不见 plan。  
- 人只坐在最高后果、最低可逆处（merge / 选型），别当中间最慢节点。

**可落地启示**
- 先建能大声失败的 gate，再画车道，最后才加学习边。  
- 审计现有流水线：标出「假边」往往是最大提速。  
- 被接受的结果要沉淀为 splitter 约束，否则系统永远快但不聪明。

**与其他层关系**  
相对昨日 LangChain「叠环」与「何时上图」：本文更偏 **loop 在节点内、graph 在节点间** 的施工细则，尤其是返回路径与 blast-radius 门。Harness（工具、权限、证据）被默认需要，但文内重心在编排几何。

**评价/局限**  
实操密度高、金句多；文末导向付费课程/社群，读架构时自行剥离。对 harness 七子系统不如 Field Guide / 源码论文细。

## 3. Graph · 「图是地图，环是行走」——何时上图、何时别装新范式

**标题：** Graph Engineering: The Layer After Loop Engineering  
**作者/来源：** DZone（署名 CORE）  
**链接：** https://dzone.com/articles/understanding-graph-engineering  
**时间：** 2026-08-14 · 抓取 2026-09-09（X 线索 @VidyasagarMSC 等）

**原文关键段落**
> graph engineering is the practice of designing how multiple specialized agents or steps connect, not the internal cycle any one of them runs. … the graph is the map, the loop is the walk. … A single agent working alone is just the smallest possible version of this same shape: one node, with an edge that points back to itself. … The stack is cumulative, not a ladder you climb away from. … If most of the honest answers land in the left column, you're describing a loop that someone talked you into over-architecting. … the technology mostly isn't new. What's newer is a shared vocabulary for a design decision these frameworks always asked of you anyway.

**翻译**
> Graph engineering 是设计多个专用 agent/步骤如何连接，不是单个 agent 内部循环。……图是地图，环是行走。……单独一个 agent 只是最小同构：一个节点，边指回自己。……栈是累积的，不是爬完就扔掉下层。……如果诚实答案大多落在「loop 就够」那一列，你描述的是被人忽悠去过度架构的 loop。……技术大多不新；新的是给框架一直要求你做的设计决策一个共享词汇。

**问题背景**  
作者此前写过 loop engineering；读者追问「环套在什么上面」。再叠加 2026 年中 X 上 graph 热潮与「是不是就是 LangGraph」的质疑，本文给出定义、对照表与降温结论。

**核心论点与论证脉络**
- 三件套：nodes / edges / shared state；并澄清 ≠ knowledge graph / GraphRAG。  
- 层栈：Prompt → Context → Harness → Loop → Graph；上层失败若下层弱，只会「更精致地难 debug」。  
- 上图信号：可分专科交接、真并行再汇合、阶段工具/模型不同、独立审核节点、失败隔离；否则保持单 loop。  
- 框架对照：LangGraph / AutoGen GraphFlow / Google ADK / A2A——技术先于术语；创作者质疑「新范式」是公平的，作者主张 **命名设计决策** 而非发明新能力。  
- 实践类比：SRE 事故 agent 的「可检查集合」是 graph，策略是 loop；找不到路径时别怪模型。

**方法/架构要点**  
开建前清单：先试 loop；节点须真专科；先画边再写码；共享状态谁可写要设计；审核节点要有牙；失败隔离；优先用现成框架别手搓编排运行时。

**可落地启示**
- Debug 时先问：是节点弱，还是图上根本没有通向根因的边？  
- 「隐式图仍是图——只是坏了才看得见」：值得把路由做成可检查结构。

**与其他层关系**  
与昨日 LangChain *3 Years of Graph Engineering* 同层同调（循环一等公民、开放研究可退回 harness），本文更强调 **词汇降温** 与基础设施类比（Terraform graph / service mesh）。相对 Hanako：Hanako 教施工细节，DZone 教选型与层栈位置。

**评价/局限**  
判断冷静、表格好用；深度实现与源码级证据弱于 Paul Serban / arXiv 论文。部分框架能力描述随版本会漂。

## 4. 三层合一 · 带代码的诊断顺序：权限与硬停步最值钱

**标题：** Agent Harness Engineering, Loop Engineering, and Graph Engineering: The Architecture of Reliable AI Agents  
**作者/来源：** Paul Serban  
**链接：** https://blog.paulserban.eu/post/agent-harness-engineering-loop-engineering-and-graph-engineering-the-architecture-of-reliable-ai-agents/  
**时间：** 2026-07-22 · 抓取 2026-09-09

**原文关键段落**
> A harness governs a single agent's relationship with its environment. A loop governs the control flow of a single agent's execution over time. A graph governs how multiple agents, tools, and checkpoints relate to each other across an entire application. Confusing the layers is common and costly… Of the three layers, the harness's permission model returns the most safety and reliability per hour invested… The second highest-leverage investment is an externally enforced loop-stopping condition… Graph structure, by contrast, is the layer to under-invest in until the application genuinely demands it. … A model taking an action it should not have taken is a harness problem. A model that never stops, or stops too early, is a loop problem. A workflow that is hard to reason about because responsibilities are smeared across one enormous prompt is a graph problem waiting to be made explicit.

**翻译**
> Harness 管单个 agent 与环境的关系；loop 管单次执行随时间的控制流；graph 管整应用里多 agent/工具/检查点如何相连。混层既常见又昂贵……三层里，权限模型每小时投入回报最高……第二杠杆是**代码强制**的停环条件……Graph 结构则应欠投资，直到应用真需要。……不该做的动作 = harness 问题；停不下来或停太早 = loop 问题；责任糊在超长 prompt 里难推理 = 该显式化的 graph 问题。

**问题背景**  
生产 agent 耗时很少在「选模型」，而在工具权限、重试上限、多阶段接线。作者用可替换的 TypeScript harness + Python loop + Python graph 示例，把三层拆成独立可测组件，并给出事故诊断顺序。

**核心论点与论证脉络**
1. Demo 的 while+tools 在长任务上死于超时、上下文溢出、自我授权失败——这些不是 prompting 问题。  
2. Harness：工具注册、permission tier（auto/confirm/denied）、上下文压缩。  
3. Loop：max_steps、连续错误上限、final_answer / request_human / tool_call；停条件外置。  
4. Graph：节点是完整 harness+loop；条件边可回边（非纯 DAG）；`max_transitions` 与 `max_steps` 同理。  
5. 80/20：先权限 + 硬停步；图结构等任务真分解再上。

**方法/架构要点**
- 心智模型：车间（harness）/ 班次（loop）/ 组织图（graph）；或 sandbox+retry+workflow 引擎。  
- 图状态用显式 typed object，而非隐式对话史，以便单节点单测。  
- 随模型变强：loop 治理可略轻，**harness 更重要**（更能干也更敢越权）；部分多节点工作可塌回单 harness loop，真多阶段仍需要 graph。

**可落地启示**
- 事故先按层归类，再动手——别默认改 prompt。  
- 新工具默认 confirm，能力一变就复查 tier。  
- 每一步记 decision/tool/result/error count，让失败可回放。

**与其他层关系**  
把 Field Guide 的「环境」、Hanako/DZone 的「环与图」收成同一诊断坐标系；引用 Anthropic harness 文、LangChain loop/graph 文、12-Factor Agents、ReAct——与昨日 digest 的源材料互通。相对 InterSystems「Gen3=抛弃预定义 DAG」叙事：本文更平衡——图不是过时，而是**欠投资到真需要**。

**评价/局限**  
代码骨架清晰、可直接当教学脚手架；示例是最小实现，生产还要补观测、幂等与真实审批通道。日期较早（7 月），未纳入 8–9 月源码级论文细节，但不影响分层诊断价值。

## 今日速览
1. **排障**：六桶命名 → 对层下刀；混层是最贵的 debug。  
2. **Harness**：合同、网关、编译态记忆、环外策略、证据收据；建完要会删。  
3. **Loop/Graph**：check 要可编程；纠错边 + 学习边；门看爆炸半径不看自信；单 agent = 自环单节点图。  
4. **投资顺序**：权限模型 + 外部停环条件 ≫ 过早上多节点图。
