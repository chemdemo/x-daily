## 1. Harness × Loop · 工业长环：playbook 瘢痕组织 + 双演化

**标题：** Auto-RecSys: Harnessing Autonomous Research Agents for Industry-Scale Recommender System（论文）+ Harness Engineering Explained: What Meta's Auto-RecSys Means…（工程解读）  
**作者/来源：** Ming Li, Dai Li, Xuying Ning 等（Meta）· arXiv:2609.10922；解读 AJ Awan · Flowtivity  
**链接：** https://arxiv.org/abs/2609.10922 · HTML https://arxiv.org/html/2609.10922 · 解读 https://flowtivity.ai/blog/what-is-harness-engineering/  
**时间：** 论文约 2026-09-09/10 · 解读发表 2026-09-12 · 抓取 2026-09-14（近五日 digests 未展开；@omarsar0 等作高信号线索）

**原文关键段落**
> Auto-RecSys addresses these challenges through three harness designs: (1) distributed asynchronous execution for running multiple experiments in parallel across servers, (2) centralized cross-server memory for persistent and recoverable execution across sessions and failures, and (3) cognitive-procedural separation, where natural-language skill files guide LLM reasoning while deterministic scripts enforce operational correctness. Auto-RecSys further employs a dual-loop self-evolving architecture: an Execution Evolution Loop in which model-specific playbooks accumulate operational knowledge by recording failed attempts and crystallizing successful pipelines, and an Idea Evolution Loop in which experimental outcomes inform subsequent ideation. … The separation is important because LLM reasoning is flexible but imprecise, while state management requires exactness: a single wrong field in a JSON state file can corrupt an entire experiment lifecycle … During stabilization (iterations 5 to 20), … reducing major fixes from 4.0 to 1.3 per iteration. … the post-transition phase (iterations 26 to 31) reached 0.5 major fixes per iteration, with 5 of its 6 iterations requiring no operational fix at all … The playbook … accumulated … 49 dead ends and 17 error-fix patterns …

**翻译**
> Auto-RecSys 用三块 harness 设计应对挑战：（1）跨服务器的分布式异步执行，并行跑多路实验；（2）集中式跨服务器记忆，让会话/故障后仍可恢复；（3）认知–程序分离：自然语言 skill 引导推理，确定性脚本强制操作正确性。系统还有双环自演化：Execution Evolution Loop 用 per-model playbook 积累失败与成功管线；Idea Evolution Loop 用实验结果喂下一轮构思。……分离之所以必要：LLM 灵活但不精确，状态管理要求精确——JSON 状态文件错一个字段就能毁掉整条实验生命周期。……稳定期（第 5–20 轮）重大运维修复从每轮 4.0 降到 1.3；基线切换后再学习，第 26–31 轮降到 0.5，且 6 轮里有 5 轮零运维修复。……成熟 playbook 积累了 49 条 dead ends 与 17 类错误修复模式。

**问题背景**  
小规模 auto-research（分钟–小时反馈）可以串行试错；工业推荐模型一次训练要数天、配置上千行、GPU 作业会抢占/坏 checkpoint/包版本冲突。瓶颈不只是「会不会出主意」，而是：**并行探索、跨会话恢复、以及别把昂贵失败再付一遍学费**。

**核心论点与论证脉络**
1. **两个挑战改写系统设计**：长反馈环 → 必须分布式并行 portfolio；系统复杂度 → 必须持久恢复 + 积累运维知识。  
2. **三块 harness 模式**：异步状态机（每 idea 独立状态文件，失败不污染邻居）；集中记忆（registry / playbooks / history / session trajectories）；认知–程序分离（skill 管判断，脚本管写状态与 API）。  
3. **双演化环**：
   - **Execution**：轨迹蒸馏进 markdown playbook——dead ends（瘢痕）+ pipeline recipes（肌肉记忆）+ submission configs（钉死的基础设施参数）；  
   - **Idea**：append-only 实验史做去重、剪枝、组合部分成功、找未探索区。  
4. **度量诚实**：墙钟多半被训练占满，系统真正移动的是 **人均注意力带宽**——人手从「每 idea 数小时–数天」压到人在环模式下的「分钟级」，同注意力可覆盖十余条并行 idea。  
5. **自愈与自改基础设施**：学到某代 GPU 不稳定就自动换代；发现监控 agent 因上下文堆积 3–5 小时静默死掉后，自行设计 cron 式「每 tick 干净 prompt」替换；某 publish 步连败四次后改 workflow 跳过该步。  
6. **已知缺口（论文自述）**：playbook 更新缺少 SkillOpt 式验证门；交互/自治仍是二元开关；跨模型知识迁移与团队级共享 backlog 仍是未来工作。

**方法/架构要点**
- 状态机：`ideating → implementing → validating → training → analyzing`（失败进 debugging）；interactive 在 idea 选择 / code review / 提交训练 / 结果评审四处停。  
- 知识三层：模型无关 orchestrator skill → per-model playbook → per-idea 临时状态。  
- One-shot transfer：第一个模型的成熟 playbook 结构可当模板，后续模型只填槽位。  
- 代码 harness 写结构化状态；自然语言 harness 给人与 LLM 读——和「让 LLM 自由改 JSON 状态」刻意相反。

**可落地启示**
- 今天下午：给一条会重复失败的运维路径开一份 markdown「死胡同表」——错误 / 根因 / 修复 / DO NOT；下次同错先查表再动手。  
- 任何会被 LLM 写坏就灾难的东西（状态文件、registry、幂等键）→ 脚本 + schema，不要 prompt 礼貌。  
- 长任务默认假设「会话会死、服务器会换」：轨迹落盘 + 跨机可恢复，比「更长上下文」优先。  
- 改 playbook / 规则时补一道轻量验证门（与 SkillOpt / Procedural Graph 的 held-out 门同构）——论文自己也承认这块欠账。

**与其他层关系**  
几乎完整落在 **harness（持久态、脚本边界、恢复）** 与 **loop（双演化环、人在环检查点）**；并行 portfolio 轻触 graph（多 idea 协调），但拓扑仍是状态机而非任意 DAG。相对 Sep 13 Tata 零信任云工程：那边强制证据门与爆炸半径；本文强制「运维知识复利」与跨会话恢复。相对 Sep 10 Procedural Graph：那边演化的是程序图拓扑；这里演化的是自然语言 playbook。相对 Sep 12 Arize：Arize 钉完成门与指纹；Auto-RecSys 钉 dead-end 目录与提交配方结晶。

**评价/局限**  
目前把「harness 让工业长环变可靠」讲得最硬的一手证据之一（31 轮、基线切换自然实验、transcript 级机制）。领域偏推荐系统 / Meta 内网工具面，迁移时要替换提交与监控适配层。解读文有咨询导流，读数字与设计时以论文 HTML/PDF 为准。Playbook 无验证门是真实风险——别把「agent 自己写进 DO NOT」当成已证明安全。

## 2. Harness · 弱模型：别加 prompt，加「不许相信模型自白」的系统

**标题：** The harness, not the model: how to make a weak or local model reliable enough to ship  
**作者/来源：** Amariah Kamau（NorahLabs / Atlarix）· DEV Community  
**链接：** https://dev.to/amariahak/the-harness-not-the-model-how-to-make-a-weak-or-local-model-reliable-enough-to-ship-2plp  
**时间：** 发表 2026-09-11 · 抓取 2026-09-14

**原文关键段落**
> A weak model doesn't need a bigger prompt. It needs a system that catches its mistakes instead of trusting them. … Never let the model be the judge of whether its own change succeeded. Check the world. … If a rule matters, the harness should enforce it mechanically, so a model that "forgets" the rule physically can't break it. … Contain execution at the OS level, so the blast radius of a bad call is bounded by the system, not by the model's judgment. … Retrieve narrowly and on demand. … Stack them and something surprising happens: the model's reliability stops being the ceiling. The system's guarantees become the floor, and a weaker model operating above a solid floor beats a stronger model operating on trust.

**翻译**
> 弱模型不需要更大的 prompt。它需要一套抓住错误、而不是相信错误的系统。……永远别让模型当自己改动是否成功的法官。去查世界。……若一条规则真重要，harness 应用机械方式强制——模型「忘了」也物理上绕不过。……在 OS 层收容执行，让坏调用的爆炸半径由系统界定，而不是由模型判断。……窄而按需检索。……叠起来会发生一件反直觉的事：模型可靠性不再是天花板，系统保证变成地板——站在硬地板上的弱模型，打得过靠信任运转的强模型。

**问题背景**  
本地 / 量化模型常见失败不是「完全不会写」，而是 **自信的假完成**：报告已改、磁盘未变；宣布完成、测试全红。团队本能是换更大 API——作者认为大半其实是缺 harness，而前沿模型只是更能「部分补偿」缺失的脚手架。

**核心论点与论证脉络**
1. **四条机制（都不要求更好模型）**：
   - 对照现实验证编辑（重读磁盘；非零退出码则卡住回合，不许宣告完成）；  
   - 控制放进 harness 而非 prompt（审批闸、等待态、完成门）；  
   - OS 级沙箱（Landlock / AppContainer / Seatbelt）+ diff 级接受/拒绝；  
   - 按需检索（ripgrep/glob）+ 耐久笔记，反对整仓塞进上下文。  
2. **错误分类**：Wrong-but-flagged 可恢复；Wrong-but-confident 才会把 bug 送进主线。  
3. **诚实边界**：Atlarix 在 Remix / Caddy / Traefik / Valkey 等有可核验合并记录，但是 **人驾驭 + 人审 + agent 联合署名**，不是「无人 AI 独自合进 Remix」。主张收窄为：好 harness + 中等模型 + 懂目标的人，能过与人类贡献者相同的门。

**方法/架构要点**
- 完成门绑定仓库自己的检查（`tsc` / `eslint` / `pytest`…），不是绑定模型叙事。  
- Prompt 里每条 always/never：问「若模型忽略会怎样？」——会坏事的那条，迁出 prompt，变成闸门。  
- 评论区补充：字符串「出现了」≠ 改对了位置；真正裁判仍是项目退出码；弱模型可能在 A/B 振荡，仍需 retry budget / 重规划逃生舱。

**可落地启示**
- 今天下午：在现有 loop 里加两行——编辑后 `read` 校验；测试非零则 `continue` 而非 `return`。  
- 审计 system prompt：把「保证类」句子改成代码路径上的硬门。  
- 本地模型优先投 harness ROI：强模型错误更隐蔽，弱模型错误更响——响的错误是礼物。

**与其他层关系**  
纯 **harness**（证据、权限、沙箱、上下文供给）；完成门与「卡住回合」直接服务 **loop 的验证/停步**。相对 Sep 13 freeCodeCamp 五部件：本文把「弱模型压力测试」写成可抄原则。相对 Sep 12 Arize：同「自白不是证据」，本文把原则压到本地/开源模型场景。相对 Auto-RecSys：那边用脚本保证状态精确；这边用磁盘重读与退出码保证编辑真实——同构的「认知–程序分离」。

**评价/局限**  
短、锋利、可当天落地；Atlarix 是参考实现，文中原则可移植。合并故事需按作者自述的窄口径阅读。未展开多 agent 图与长程 playbook——作者刻意停在「单工人 + 硬地板」。

## 3. Harness · 外层控制论：guides / sensors，再按「调节什么」切三类

**标题：** Harness engineering for coding agent users  
**作者/来源：** Birgitta Böckeler · martinfowler.com  
**链接：** https://martinfowler.com/articles/harness-engineering.html  
**时间：** 全文发表 2026-04-02（取代 2 月 memo）· 抓取 2026-09-14（近几日 digests 多次点到 Fowler/ambient affordances，尚未整篇展开本 taxonomy）

**原文关键段落**
> A well-built outer harness serves two goals: it increases the probability that the agent gets it right in the first place, and it provides a feedback loop that self-corrects as many issues as possible before they even reach human eyes. … Guides (feedforward controls) … Sensors (feedback controls) … Particularly powerful when they produce signals that are optimised for LLM consumption, e.g. custom linter messages that include instructions for the self-correction — a positive kind of prompt injection. … Computational — deterministic and fast … Inferential — Semantic analysis, AI code review, “LLM as judge”. … Maintainability harness … Architecture fitness harness … Behaviour harness … Harnesses are an attempt to externalise and make explicit what human developer experience brings to the table, but it can only go so far. … A good harness should not necessarily aim to fully eliminate human input, but to direct it to where our input is most important.

**翻译**
> 建得好的外层 harness 做两件事：提高 agent 第一次做对的概率；并在问题到达人眼前之前，用反馈环尽量自纠正。……Guides（前馈）……Sensors（反馈）……当传感器信号为 LLM 消费优化时特别强——例如带修复说明的自定义 linter 报错，一种正向 prompt injection。……Computational：确定、快速……Inferential：语义分析、AI code review、LLM-as-judge。……可维护性 harness / 架构适应度 harness / 行为 harness……Harness 试图把人类开发者经验外化、显式化，但只能走到一定程度。……好 harness 不必以消灭人类输入为目标，而应把人类注意力导向最关键处。

**问题背景**  
「Agent = Model + Harness」定义太宽：厂商内置运行时是 harness，用户在仓里加的 AGENTS.md / hooks / 结构测试也是 harness。需要一张 **用户侧外层 harness** 的地图，否则讨论会在「又加一条 skill」与「又加一个评审 agent」之间打转。

**核心论点与论证脉络**
1. **有界语境**：本文专讲 coding agent 的 **outer harness**（用例如系统之上、由用户/团队装配）。  
2. **二维控制**：前馈 Guides × 反馈 Sensors；再交叉 Computational（lint/测试/ArchUnit）vs Inferential（skills、LLM judge）。只做反馈 → 反复犯同一错；只做前馈 → 从不知规则是否生效。  
3. **转向环（steering loop）**：人的工作是迭代 harness——同一问题多次出现，就改进 guide/sensor；也可用 agent 帮写结构测试、从模式草拟规则。  
4. **质量左移**：按成本/速度把传感器铺在 commit 前 / 集成后 / 持续漂移监控 / 运行时 SLO。  
5. **三类调节目标**：
   - Maintainability：重复代码、复杂度、覆盖率、风格——计算型传感器最稳；  
   - Architecture fitness：性能/可观测性等 fitness functions；  
   - Behaviour：功能正确性仍是大象——「AI 写的测试绿灯 + 一点手测」对高自治不够；approved fixtures 等只在局部好用。  
6. **Harnessability / ambient affordances**：强类型、清晰模块边界、框架抽象提高可治理性；绿野可先天烘焙，遗留债最重处恰恰最难套 harness。  
7. **Harness templates + Ashby**：企业常见服务拓扑可收成「guide+sensor 包」；用拓扑收窄变异度，才可能建得起全面调节器。  
8. **人的角色**：经验、审美厌恶、组织对齐、问责感无法完全外化——harness 的目标是 **重定向** 人类注意力，不是假装可删人。

**方法/架构要点**
- 失败模式映射：结构问题 ← 计算传感器；语义重复/过度工程 ← 昂贵推理传感器；误诊/误解需求 ← 任何传感器都不可靠，规格本身要先清楚。  
- 与 context engineering：后者是把 guides/sensors **投递给**模型的手段；用户 harness 是一种有任务边界的 context engineering。  
- 开放题：guides 与 sensors 如何保持一致不互相矛盾？如何评估 harness 覆盖率（类比 mutation testing）？如何把散落控制收成可配置系统？

**可落地启示**
- 评审话术：先标这条控制是 guide 还是 sensor、计算还是推理、调节的是可维护性/架构/行为哪一类。  
- 优先加「带修复说明的计算型传感器」（自定义 lint）——便宜且对弱/强模型都有效。  
- 别指望行为 harness 已有银弹；高自治前先诚实对待「AI 测 AI」的信任链。  
- 选技术栈时把 harnessability 写进决策：遗留系统要先还结构债，再谈无人值守。

**与其他层关系**  
定义 **用户侧 harness 控制论**；steering loop 是 **loop 第 4 环（改环境）** 的组织版。相对 Auto-RecSys playbook：那边是生产研究系统的瘢痕记忆；本文是通用「前馈/反馈」语言。相对 Kamau：Kamau 给四条硬原则；Birgitta 给分类账与「行为层仍欠」的清醒。相对 Sep 12 FutureAGI「坏决策 vs 坏执行」：本文再把「坏执行」拆成缺 guide / 缺 sensor / 传感器类型错配。

**评价/局限**  
目前把 harness 讨论抬到「控制系统设计」最清楚的长文之一；案例来自 OpenAI 内部、Stripe minions、Thoughtworks 实战，可操作但不绑单一厂商。日期较早（4 月），未纳入 8–9 月源码解剖与 Auto-RecSys；行为 harness 一章明确「仍未解决」。GenAI 辅助写作已披露。
