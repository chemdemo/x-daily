## 1. Harness · 行为评测当「集成测试」：别只看期末总分

**标题：** The Anatomy of Harness Engineering: How to Evaluate, Iterate, and Guard AI Coding Agents  
**作者/来源：** Taylor Mullen（Principal Engineer）、Christian Gunderman（Staff Software Engineer）· Google Developers Blog  
**链接：** https://developers.googleblog.com/en/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/  
**时间：** 发表 2026-09-09 · 抓取 2026-09-11

**原文关键段落**
> When developers first work on harness engineering for agentic coding systems, they often fall into the same trap: they run common end-to-end benchmarks like Terminal-Bench and DeepSWE, watch a composite score move by a few percentage points, and have no idea why it changed. … Behavioral evaluations function like integration tests for improving agent harness operation. … The primary purpose of an evaluation suite is not to celebrate when you make the agent 2% better; it is to give you unshakeable confidence that a new prompt tweak, tool schema change, or model upgrade did not make the agent holistically worse. … Assert behavior, not output prose.

**翻译**
> 开发者刚做编码 agent 的 harness 工程时，常掉进同一陷阱：跑 Terminal-Bench、DeepSWE 一类端到端基准，看总分挪几个百分点，却完全不知道为什么变了。……行为评测像改进 harness 的集成测试。……评测套件的首要目的不是庆祝 agent 又好了 2%，而是给你不可动摇的信心：新的 prompt 微调、工具 schema 变更或换模型，没有把系统整体弄坏。……断言行为，而不是断言输出散文。

**问题背景**  
端到端「期末考试」能告诉你目的地有没有到达，却回答不了「是模糊 prompt 上过度自信、忘了跑测试、还是幻觉了一个 CLI flag」。换模型或改 harness 时，缺的是可定位、可回归的微观信号。

**核心论点与论证脉络**
1. **成绩单 vs 行为路标**：E2E 基准适合筛查与宏观对比；真正支撑迭代的是对离散、可观察动作的断言（是否先澄清、是否跑本地校验器、文档是否给规范仓库链接）。  
2. **时机**：从零搭 agent 时先靠 dogfooding；等它能处理自家样板与例行开发任务后，再进入「保证前进、防止回退」的第二阶段。  
3. **架构**：把行为断言拆成可本地跑的确定性、类单元检查；复杂任务避免强制死板工具序列，改用更模糊的结果导向检查（含 LLM-as-judge）。  
4. **自动化 prompt**：丰富行为套件后，可让 LLM 改 system prompt 直到失败用例通过，同时其余用例当 CI 护栏。  
5. **批量而非单次拦 PR**：模型非确定性会让单次评测嘈杂；用批量聚合通过率看趋势。

**方法/架构要点**
- 三步环：挑一个失败模式 → 按任务复杂度写灵活断言 → 自动化批量监控稳定性。  
- 示例断言：天气问题必须调用 web search，而不是「答案听起来像」。  
- Macro E2E + micro behavioral 互补：前者验终点，后者做安全快速迭代伙伴。

**可落地启示**
- 下次分数掉了，先问「缺哪条行为断言」，别先加形容词到 prompt。  
- 评测 KPI 改成「改 harness / 换模型时的置信」，而不是「刷榜 2%」。  
- 每个修过的真实失误，沉淀成一条行为回归用例。

**与其他层关系**  
落在 **harness 的反馈/证据子系统**；批量行为环直接服务 **loop 第 2 环（验证）与第 4 环（爬山改 harness）**。相对昨日 Vinayak「验证变稀缺」、Yarchi「独立验收」：本文给出 Google 侧可执行的评测形状。相对 Field Guide 的证据门：把门从「单次运行」拉到「持续工程」。

**评价/局限**  
短、清晰、可立刻开工；示例偏 Google Antigravity / 编码 agent。未展开生产在线评测与领域 criteria drift（见补充 Hugo 文）。产品化细节指向 Agent Platform / agents-cli，读架构时自行剥离。

## 2. Harness · 生产走流程：FeedAgent 的「保龄球护栏」

**标题：** Building a Robust Harness for agent in production: Feed agent case-study  
**作者/来源：** Kamie Shami-Schnitzer · monday.com AI Engineering  
**链接：** https://engineering.monday.com/building-a-robust-harness-for-agent-in-production-feed-agent-case-study/  
**时间：** 发表 2026-09-09 · 抓取 2026-09-11

**原文关键段落**
> Think of an AI agent flow like bowling: the task is executed as a ball on the surface – which is the LLM, and the harness like the bumpers on the sides of the lane. Without them, one bad roll and you’re in the gutter… We decided to build the harness by ‘walking the flow’ – going over each phase of the agent’s execution flow… asking, “What can go wrong here, and what does the harness do about it?” … We used LangChain’s agent architecture with the built-in harness. Then we expanded and built our own harness around it, which is business-specific. … The bumpers don’t guarantee a strike. They guarantee the ball stays in the lane.

**翻译**
> 把 agent 流想成保龄球：任务是球，LLM 是球道面，harness 是两侧护栏。没有护栏，一次坏球就进沟。……我们用「走流程」建 harness：逐步走过执行各阶段，每一步问「这里会出什么错，harness 怎么兜？」……先用 LangChain 内置 harness，再按业务域包一层自己的。……护栏不保证全中，只保证球永远留在道上。

**问题背景**  
feedAgent 要为每个工作区成员策展个性化活动流：多源真实数据、结构化可行动输出、每条必须引用真实活动、用户直接可见——典型「能胡编但绝不能胡编进产品」场景。

**核心论点与论证脉络**
三大出错面：**Data & Context / Agent Flow / Feedback Loop**。方法不是堆通用 checklist，而是沿一次真实跑法逐步钉护栏。

1. **调用前（数据）**：确定性预处理器压缩事件洪峰、去 PII；**别名系统**替换原始 ID，输出再解析别名——发明的引用直接丢弃；系统 prompt **缓存**降本。  
2. **初始化**：输出 schema 强制经校验的 tool call（合同而非希望）；schema 失败带错误重试；`modelCallLimitMiddleware` 安全结束。  
3. **运行中**：递归上限与模型调用上限双界；必做工具从「可选菜单」拆出、放到环外保证发生；工具错误信息要可行动（「用现有数据继续」vs 裸 `failed`）。  
4. **输出后**：幻觉过滤 + 跨条目去重。  
5. **观测与学习**：LangSmith 全轨迹；每次跑发汇总事件；**Feed Memory**——显式规则（高权威、确定性应用）+ 行为推断（低权威、软上下文）；离线 CI eval + 在线生产分析。

**方法/架构要点**
- 「走流程」= 尊重 agent 是复杂 loop，不是固定管道。  
- 业务 harness = 通用运行时 + 域专用预处理 / 别名 / 记忆 / 评测。  
- 必须发生的步骤不要交给「模型自由选工具」。

**可落地启示**
- 今天就能做：给工具失败写「下一步指令」式错误消息；把必做步骤挪出 agent 菜单。  
- 幻觉面：能用别名/白名单 ID 的地方，别让模型直接吐生产主键。  
- 学习环分权威：用户明说的规则 ≠ 从点击推断的偏好。

**与其他层关系**  
几乎全在 **harness**（上下文编译、工具网关、证据、痕迹）；递归/调用双上限是 **loop 硬停**；Feed Memory 跨跑反馈靠近 **loop 第 3–4 环**。相对昨日 Yarchi 六决策：本文是「已上线产品」版施工日志。相对 Google 文：monday 同时强调离线+在线 eval。

**评价/局限**  
生产气味足、阶段划分清楚；深度实现代码少，依赖 monday 内部 skills。LangChain 细节会随版本漂。未展开多 agent 图拓扑——作者刻意停在单 deep agent + 业务护栏。

## 3. Graph · 区别不在拓扑，在「谁在何时决定下一步」

**标题：** Graph Engineering: When an Agent Loop Should Be a Graph  
**作者/来源：** Sangam Pandey  
**链接：** https://sangampandey.info/blog/graph-engineering-agent-loops-to-graphs  
**时间：** 发表 2026-07-27 · 抓取 2026-09-11（近三日 digests 未深写；与 DZone/Hanako 互补的「成本与决策时刻」轴）

**原文关键段落**
> Graph engineering is the practice of deciding an agent workflow's control flow before the agent runs, by drawing the workflow as a graph and generating the orchestration code from that drawing. It matters because control flow decided at authoring time costs nothing per run, while control flow decided at inference time is billed on every iteration forever. … A loop is a graph. It is a graph with one node and an edge pointing back at itself. … The distinction is when the routing decision happens. … Can you draw the workflow without running it? … A graph cannot discover a step you did not draw.

**翻译**
> Graph engineering 是在 agent 跑之前就决定控制流：把工作流画成图，再生成编排代码。关键在于——作者时决定的控制流每次运行零成本；推理时决定的控制流每一轮都在烧钱。……Loop 就是图：一个节点加一条指回自己的边。……真正的区别是路由决策发生在何时。……你能不能在不跑的情况下画出整张工作流？……图发现不了你没画出来的那一步。

**问题背景**  
7 月「画张图丢给编码 agent」三行菜谱刷屏后，最高赞回复是四字：*how is this not a loop?* 作者认为这才是真问题，并给出可操作的成本表与选型测试。

**核心论点与论证脉络**
1. **不是知识图谱**；是控制面。新意在作者步骤变便宜（手绘 → 生成脚本），瓶颈从「表达图」移到「决定图画什么」。  
2. **Loop = 推理时路由（每轮付费、难评审）**；**Graph = 作者时路由（付一次、边是代码、可当评审工件）**。  
3. **成本**：缓存前缀稳定性——图几乎白嫖稳定前缀；loop 必须刻意钉死 system/spec，否则最贵。协调开销会让多 agent 比单 agent 更贵且未必更准。  
4. **一分钟测试**：能不跑就画完 → 图；画到第三步取决于返回值 → 环。开放研究、未知根因调试属环领地。  
5. **生产画法**：先画失败边；标独立节点拿并行；图与生成代码同仓；每节点一职。  
6. **四种翻车**：未画边 / 过早上图 / 刚性重试（输入不变）/ 假独立并行。  
7. **证据诚实**：前提（上下文腐烂、缓存经济）扎实；「菜谱优于纪律环」尚无对照实验——当 convergent practice，别当已证定理。

**方法/架构要点**
| 模式 | 谁决定下一步 | 主失败模式 |
|---|---|---|
| 单会话 | 模型持续 | 上下文腐烂 |
| Loop | 模型每轮 | 路由 token 复利、推理跨轮丢失 |
| Graph | 你在作者时 | 需要一条没画的边 |

**可落地启示**
- 开工前先试画：画得动就图，画不动就去钉 loop 的前缀与停条件。  
- 失败边画在 happy path 之前——编码 agent 最会瞎编的就是你没写的超时/空返回。  
- 重试边必须改变至少一个条件，否则只是更慢地失败。

**与其他层关系**  
相对 9/9 DZone「图是地图、环是行走」与 Hanako「loop 在节点内」：本文把分歧钉在 **计费与可评审性**。相对昨日 Procedural Graph：那边是可演化程序记忆；这边是作者时静态/半静态控制面。Harness（权限、证据）仍是节点内前提。

**评价/局限**  
概念手术刀级清晰，表格与失败模式清单可收藏；日期较早，未纳入 9 月 Procedural Graph / HarnessDev。对「手绘→生成」可靠性偏乐观，需自备评审与测试。

## 4. Graph · Claude workflow 施工：假边、菱形、verifier 与可收敛 cycle

**标题：** Graph Engineering：别再把你的 Agents 串成链  
**作者/来源：** seeco (@seeconvm) · X Article  
**链接：** https://x.com/seeconvm/article/2088199384580108339  
**时间：** 发表 2026-08-14 · 仓库归档 `articles/2026-08-14-graph-engineering-stop-chaining-your-agents/`（英文 `article.md` 为占位，正文见 `article_zh.md`）· 抓取 2026-09-11（近三日未深写）

**原文关键段落**
> 我打开过的几乎每一个多步骤 agent，都是一条队列。……Prompt 是一句话。Loop 是一个循环。Harness 是你的 agent 站立的地板。但工作本身的形状……是一张 graph。节点负责思考。边搬运结果。… 对你 agent 里每一个「然后」：下一步是否真的读取了上一步的输出？如果没有，那里就没有边，等待纯属浪费。… 把 agents 留给判断。别留给管道工程。每条边都是一个 agent 的 graph，等于在为自己的接线交房租。… 对「见过的一切」去重，而不只是对已确认结果。

**翻译**  
（原文为中文；要点同上。）多步骤 agent 常被写成队列；「然后」≠ 依赖。Harness 是地板，graph 是工作形状。剪掉不传数据的箭头；flatten/dedupe 用代码当边，别再拉一个 agent；cycle 必须对 *seen* 去重否则永远干不了。

**问题背景**  
Claude Code 动态 workflows 已能让编排脚本（JS）零模型 token 地调度 subagent 舰队。缺的是一张从「线性脚本」走到「可审计图」的 14 步地图。

**核心论点与论证脉络**
14 步浓缩为可执行原则：
1. 节点契约（有界入出 + schema）与边数据契约。  
2. `parallel()` 扇出 + barrier 扇入；菱形是主力拓扑。  
3. 条件路由：分类可模型、路由必须是代码。  
4. 边上 verifier（对抗 / 多镜头 / judge panel）。  
5. 失败局部化（null thunk + worktree）。  
6. `loop until dry`：对 seen 去重；连续 K 轮无新则停。  
7. 节点间模型分层；默认 `pipeline()`，barrier 要挣来。  
8. 让 Claude 写/存 `.claude/workflows/`。

**方法/架构要点**
- 编排在代码里 → 十八个 agent 的协调不烧对话 token。  
- 「代码更干净」不是上 barrier 的理由。  
- 本周可搭的六张图：路由 auth 清扫、deep-research、按文件移植、对抗式 diff 审查、生态扫描、未知规模发现。

**可落地启示**
- 只带走三件：剪假边；默认 pipeline；对 seen 去重。  
- 审计现有 agent：标出「假边」往往是最大提速。  
- 合并/去重步骤先问能不能用 `flatMap`+`Set`，再问要不要 agent。

**与其他层关系**  
相对 Sangam：Sangam 定「何时图」；seeco 定「Claude 里怎么建」。相对 Hanako：同构于纠错边/学习边/爆炸半径，但更贴 Claude workflow API。Harness（schema、权限、worktree）被当作节点前提。

**评价/局限**  
实操密度极高；文末有账号导流，读步骤时自行剥离。英文源文件在仓库里仍是占位符——以 `article_zh.md` / X 页为准。强绑定 Claude Code workflow 语义，换栈需改写 API，不改形状原则。

## 今日速览
1. **Harness 评测**：行为断言 = harness 的单元/集成测试；目的是换模型/改 prompt 时不整体变差，不是刷 E2E 2%。  
2. **Harness 生产**：monday「走流程」——预处理与别名、双上限、必做步骤出菜单、输出幻觉过滤、显式规则 vs 推断记忆、离线+在线 eval。  
3. **Graph 选型**：能不跑就画完才上图；区别是作者时路由 vs 推理时路由；先画失败边。  
4. **Graph 施工（Claude）**：假边测试、菱形、代码边、verifier、对 seen 去重的收敛 cycle。  
5. **投资顺序提醒**：先行为回归与生产护栏，再作者时图画边；自演化 harness（HarnessDev）仍需验证门与跨模型预期管理。
