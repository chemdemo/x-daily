## 1. Harness × Graph × Loop · 长程研究：就绪门 + 依赖图 + 带异议的聚合树

**标题：** Stellar Colosseum: A Many-Agent Harness for Long-Horizon Research in Mathematics and Theoretical Computer Science  
**作者/来源：** Honghao Lin, David P. Woodruff 等（Google Research / CMU）· arXiv:2609.15983  
**链接：** https://arxiv.org/abs/2609.15983 · PDF https://arxiv.org/pdf/2609.15983.pdf  
**时间：** arXiv 约 2026-09-14 · v2 2026-09-15 · 抓取 2026-09-16（近五日 digests 未覆盖；今日 X 新闻摘要与论文推送高信号）

**原文关键段落**
> Language models can produce plausible short proofs, but may still be unreliable on long-horizon research problems, where progress depends on a sequence of uncertain and interdependent decisions. We introduce Stellar Colosseum, a model-agnostic harness for allocating inference across research in mathematics and theoretical computer science. Colosseum explores alternative strategies before proof construction, uses a readiness gate to decide when a route is mature enough to decompose, represents the proof plan as interdependent section-level subproblems, and routes verifier findings back to the affected part of the argument. Across these stages, it generates candidates in parallel, attacks them with targeted falsification, and combines candidates and their critiques into a single research artifact through overlapping random-sample tree aggregation. … The readiness gate asks whether one of these routes is concrete enough to support a proof plan. It tests whether the remaining uncertainty can be localized within a stable proof architecture, not whether the proof has already been completed. … Substantive disagreements and falsification evidence are carried forward rather than averaged away. … On TCS-Bench, … Colosseum achieves 71.0% accuracy using Gemini 3.1 Pro and Gemini 3.7 Flash. … the proof-oriented pipeline with execution feedback solves 218 of 222 problems.

**翻译**
> 语言模型能写出像样的短证明，但在长程研究问题上仍不可靠——进展取决于一串不确定且相互依赖的决策。我们提出 Stellar Colosseum：一个模型无关的 harness，用来在数学与理论计算机科学研究中分配推理算力。Colosseum 在动笔证明前先探索多条策略，用**就绪门**判断某条路线是否成熟到可以分解，把证明计划表示成带依赖的节级子问题，并把验证器发现路由回受影响的论证片段。各阶段并行生成候选、用定向证伪攻击它们，再通过**重叠随机抽样树聚合**把候选与其批评合成一份研究产物。……就绪门问的是：某条路线是否具体到足以支撑证明计划——它测的是剩余不确定性能否被钉在稳定证明架构里，**不是**证明是否已经完成。……实质性分歧与证伪证据会被向前传递，而不是被平均掉。……在 TCS-Bench 上，用 Gemini 3.1 Pro 与 3.7 Flash 做跨模型选择可达 71.0%；带执行反馈的面向证明流水线在 222 道 Codeforces 题上解出 218 道。

**问题背景**  
短证明 / 奥赛级成功不能直接外推到「多轮探索 → 分解 → 局部修补 → 全局再验」的研究工作。四类硬伤：战略不确定、分布式技术瓶颈、长输出误差累积、失败仍含可复用局部进展——都需要**显式工作流状态**，而不是更长的单次生成。

**核心论点与论证脉络**
1. **两层架构**：（a）工作流级五阶段——策略探索 → 就绪门 → 证明分解 → 子问题求解 → 全局验证（可局部修订或退回再探索）；（b）阶段内——并行候选 → 定向证伪 → 重叠抽样树聚合。
2. **就绪门 ≠ 完成门**：过门条件是机制稳定、未决声明可分给各节、没有会改目标/架构的未决桥；中心引理仍可很难，但陈述与角色必须显式。过早分解会把猜测当架构；过晚则浪费并行宽度。
3. **分解产出真依赖图**：文档顺序管叙述；DAG 管可并行数学工作；独立节并行，失败**只重跑受影响子问题**，保留别处已接受节——这是 graph 层「真边」在研究域的实例化。
4. **证伪与聚合纪律**：证伪记录贴在候选上；聚合是建设性归约（合并兼容件、保留竞争分支、局部修补），**不是投票**；致命缺陷一票否决；干净证伪记录也可能只是测试太弱。
5. **共享研究知识**：最新失败草稿 + 验证反馈直接进下一轮；知识目录另存定理/引理、失败路线、陷阱与异议——避免聚合丢掉可复用瘢痕。
6. **结果**：开题研究若干 FOCS/JMLR 衍生开放问题有新结果（伴文）；TCS-Bench 跨模型选择 71.0%；Codeforces 218/222；工作流已接入 Google Antigravity Teamwork 的 Long Proof pattern。

**方法/架构要点**
- 候选带类型 schema（策略：机制 / 所需引理 / 预期瓶颈 / 可证伪测试；证明：假设与缺口标记）。
- 聚合树宽度形如 `(m0,…,mL)`，层间重叠抽样使期望复用约 2–3，避免「一次塞进全部候选」的上下文爆炸。
- 全局验证看整篇论证一致性（假设漂移、跨节错用依赖、目标错配），缺陷定位到节以便可行动修订。

**可落地启示**
- 今天下午：给任何「先想清楚再拆任务」的 agent 加一道就绪门——未过门禁止 fan-out 子 agent；过门产物必须是带依赖的节骨架，不是一串『然后』。
- 聚合时保留异议附件：合成答案若丢掉 falsifier 记录，等于把证伪成本白付。
- 局部重试只碰坏节：与 Tejas/Arize「按副作用恢复」、Tessl「中环改项目」同构——别因一处失败整图推倒。

**与其他层关系**  
同时落在 **harness**（模型无关推理分配与共享研究态）、**graph**（节依赖 DAG + 并行/局部修订）、**loop**（探索–证伪–聚合与修订/再探索环）。相对昨日 Hanako / ShipWithAI 候选：本文给「真边」一个研究域硬例子（依赖边 vs 叙述顺序）。相对 Auto-RecSys：那边结晶 playbook dead-ends；这边结晶证伪记录与知识目录。相对 Tata 证据门：就绪门管「能不能开拆」，全局验证管「组装后是否成证明」。

**评价/局限**  
目前把「长程研究 harness」写得最完整的一手公开工作之一；数字与 Antigravity 集成提高可信度。领域偏数学/TCS 自然语言证明（形式化检查是可选证据而非唯一裁判）；跨模型 71% 依赖选择器质量；开题「新结果」需对照伴文与人类介入披露。算力与候选宽度配置是生产迁移的隐成本。

## 2. Graph · 边 = 数据依赖；『然后』不是边

**标题：** From Loops to Graphs: The Edge That Was Never There  
**作者/来源：** ShipWithAI Senior  
**链接：** https://shipwithai.io/blog/agent-graph-engineering  
**时间：** 发表 2026-08-11 · 昨日 digest 作「下周候选」· 今日升格深写

**原文关键段落**
> An edge exists only when data crosses between two steps: the output of one is the input of the next. "And then" is not an edge. It is sequence, and a loop hands you sequence for free whether the work needs it or not. … A loop scales in depth (more iterations on one thread); a graph scales in width (independent steps run in parallel). But width is capped by Amdahl’s serial fraction, which is just a formal name for your real edges. … Two steps joined by ordering alone can run at the same time… Two steps joined by a real dependency can’t… … Our own published loop… two fixes ran back to back, and the second one never read a single byte the first one wrote. … The whole run… took 124 seconds. … A graph would section these into two lanes and finish in one pass. … Agent graph engineering is not "wire more nodes." It’s the discipline of proving, for every arrow you want to draw, that data actually crosses it, and deleting the ones where it doesn’t.

**翻译**
> 边只在数据跨过两步时存在：一步的输出是下一步的输入。「然后」不是边，只是顺序；而 loop 会免费给你顺序，无论工作是否需要。……Loop 在深度上扩展（单线程更多轮）；graph 在宽度上扩展（独立步骤并行）。但宽度被 Amdahl 串行份额封顶——那不过是「真边」的正式名字。……仅由顺序连接的两步可以同时跑；由真依赖连接的不能。……我们自己发布的 loop 里，两次修复背靠背执行，第二次**没读**第一次写出的任何一个字节。……整段跑了 124 秒。……图会把它们切成两条车道一趟跑完。……Agent graph engineering 不是「多接线」；而是对每条想画的箭头证明数据真的跨过，并删掉没有跨过的那些。

**问题背景**  
2026 年中 graph engineering 标签爆发后，大量教程把「下一步发生什么」画成边——把**顺序**与**依赖**焊死。结果是：假边 → 慢 loop 穿 YAML；漏边 → 竞态。需要一把可在自家 trace 上跑的假边测试。

**核心论点与论证脉络**
1. **定义靠 Make 1976**：节点是产物，边是产物间依赖；LangGraph「edges define what happens next」作为框架原语可以，但工程上必须拆开 ordering vs dependency。
2. **控制边 ≠ 数据边**：共享 verifier（每轮重跑 flake8）是「何时检查」，不是「读了什么」——不能拿它当串行两修复的理由。
3. **对自家四 agent 发布链做审计**：strategist→writer 薄；writer→seo / writer→reviewer 真；seo→reviewer **假**（reviewer 重做 SEO，从不读 optimizer 报告）——示意图是直线，真形状是 fan-out。
4. **Loop 是带自环的单节点图**：「告别 loop」是错讣告；该停的是「把本可并行的宽度当深度付账」。
5. **Amdahl 天花板**：串行份额 = 删不掉的真边；假边过串行化，漏边出竞态——图把依赖主张公开，不替你免思考。

**方法/架构要点**
- 五分钟审计：对最近一次 loop 的每对连续步骤问「第二步是否读了第一步的输出？」每个诚实的「否」= 被浪费的宽度。
- 词汇对照表：iteration↔node，back-edge↔cycle，stop↔sink，「and then」↔(no edge)。

**可落地启示**
- 今天下午：把一张现有编排图每条箭标成「数据 / 仅顺序 / 控制门」三色；删掉「仅顺序」箭或改成并行。
- 上 fan-out 前先写串行份额估计——没有真边清单就谈「上图加速」是空话。
- 与 Hanako「编排器持有一切会安静变差」同读：假边与中心编排器都是协调税。

**与其他层关系**  
纯 **graph** 定义文；loop 被降维成「深度轴」；harness 几乎不谈（假定已有 verifier/工作区）。相对 V12（Sep 12）「何时建图」：本文给可操作的假边测试与 Amdahl 语言。相对 Colosseum：那边依赖边控制并行数学工作；这边给通用审计刀。相对 CareerStack「loop→harness→graph」：同「别先豪华图」。

**评价/局限**  
短、锋利、有自家 124 秒收据；系列后续篇未全出。案例偏内容管线 / lint sweeper，不是云部署级证据门。作者承认「画对边是判断不是 lint」——图上的自信错边可能比 loop 空转更安静地出事。

## 3. Loop · 生产可靠性：预算 / 检测 / 重试语义 / 副作用账本

**标题：** Agent Reliability Engineering Design Guide — Retries, Loop Detection, Timeout Budgets, and Human Escalation for AI Agents  
**作者/来源：** Hidekazu Konishi  
**链接：** https://hidekazu-konishi.com/entry/agent_reliability_engineering_design_guide.html  
**时间：** 首发 2026-08-02 · **Last Updated 2026-09-15** · 抓取 2026-09-16（近五日 digests 未展开；与昨日 Tejas verify / Kamau「别信自白」同轴但覆盖面更广）

**原文关键段落**
> An AI agent that works in a demo and an AI agent that can be operated are different artifacts. … It is a design guide for the reliability of the agent execution loop: how a task is declared finished, how much the agent is allowed to spend before it must stop, how you notice that it is going in circles, what "retry" even means when the thing you are retrying is a decision rather than a request, how to keep a repeated tool call from charging a customer twice, when to hand the work to a person, and how to resume afterwards. … The single most common structural gap in production agents is … Degrade, escalate, and abort with compensation … have to be built before they can be chosen. … "the agent said it succeeded" should never be the signal that closes a task. … A step budget guarantees the loop stops. It does not guarantee the loop stops soon. … If you take one artifact from this article, take this one. The side-effect ledger is an append-only record of every externally visible effect the agent attempted…

**翻译**
> Demo 能跑的 agent 与可运营的 agent 是两件不同制品。……这是一份关于 **agent 执行环可靠性**的设计指南：任务如何被宣告完成、花多少必须停、如何发现在绕圈、「重试」在重试的是决策而非请求时意味着什么、如何避免重复工具调用向客户收两次费、何时交给人、以及如何恢复。……生产 agent 最常见的结构缺口是：降级、升级、带补偿的中止——必须在能被选择之前就建好。……「agent 说成功了」永远不该是关任务的信号。……步数预算保证环会停，不保证它很快停。……若只从本文拿走一件制品，拿走这个：**副作用账本**——对 agent 尝试过的每个外部可见效果的只追加记录。

**问题背景**  
单次模型调用的韧性（SDK 重试、断路器）≠ 四十步决策环的可运营性。控制流非确定、部分成功是常态、actor 兼 reporter、目标每步可漂移、爆炸半径是工具面——经典 SRE 词汇仍用，但要补专门设计。

**核心论点与论证脉络**
1. **三终点必须齐**：目标满足（外部可检查谓词）/ 预算耗尽 / 守卫触发——只做其一会挂死、烧满预算、或从不干净结束。
2. **三种预算不互换**：步/轮、token、墙钟；再拆**强制天花板** vs **告知模型的预算**（优雅收束 vs 截断）。
3. **三种「绕圈」**：精确重复 / 停滞（动作变、世界不变）/ 循环（A 修 B 坏）——检测器、阈值、升级路径不同；指纹必须规范化 JSON，否则模型加空格就能骗过。
4. **重试四作用域**：模型调用 / 工具调用 / 步（决策+动作）/ 任务；先问「是否已提交副作用」再问「是否可重试」；replay vs re-decide 不可混。
5. **幂等在边界不在 prompt**：effect key 来自意图（task+step+canonical args），不是每次 attempt 新 UUID；plan-then-apply 与审批闸要耐久等待。
6. **超时乘法**：`steps × step_retries × call_retries × call_timeout`；传绝对 deadline 并向下钳制；取消必须传播，否则「超时」后邮件仍发出。
7. **升级是能力不是失败分支**：handoff 包要含不可变目标、副作用账本、待决租约、停止原因、恢复句柄与安全期限。
8. **副作用账本在对话外**：compaction 会丢掉「创建了 record 4471」——账本是 resume / 补偿 / 给人接手的唯一可信源。
9. **多 agent**：子任务继承合同与预算池（禁止每人一份满分预算）；父级验证子报告；限制委托深度防级联。

**方法/架构要点**
- 明确分层：推理调用韧性另文；本文只管执行环；正确性验证 / 观测 / 安全 / 记忆各有姊妹文。
- 运行时单位对照表（Agents SDK `max_turns`、ADK `max_llm_calls`、LangGraph `recursion_limit`…）强调迁移时单位不可直接抄数字。
- 可靠性测试：断言终态而非轨迹；故障注入优先「工具成功但响应丢失」；对守卫用 stub agent 做确定性单测。

**可落地启示**
- 今天下午：为现有 loop 加上「降级 / 升级 / 带补偿中止」三条终态，并写一张工具→(compensate|reconcile|refuse) 注册表。
- 把完成谓词与副作用账本移出 transcript；compaction 后再也不靠聊天记录证明写过什么。
- 告警看率：守卫触发率、预算耗尽率、部分完成率、重复 effect 率（应为 0）。

**与其他层关系**  
几乎全部在 **loop 的生产可靠性**；完成谓词与账本直接强化 **harness**；多 agent 预算分区轻触 **graph**。相对 Tejas（昨日）：Tejas 给可跑 verify 外环；本文给检测 / 重试 / 升级 / 账本全谱。相对 Kamau / Arize：同「自白≠证据」，本文把 SRE 词汇与反模式表写全。相对 Tessl Feedback Loop：Tessl 改项目条件；本文保证单次/多次 run 失败时可运营。

**评价/局限**  
目前公开网上把 agent 执行环可靠性写到「可当设计评审清单」深度的长文之一；9/15 更新说明作者仍在维护。规范引用钉在 2026-07-31 核查——具体 API 默认值需再对当前文档。篇幅极长，适合按反模式表（§14）切片落地，不宜一次读完当教程。标签「agent reliability engineering」作者自承非正式学科名。
