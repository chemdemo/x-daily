## 1. Harness · 生产可靠性：合同、完成门、指纹检查点与按副作用恢复

**标题：** Harness Engineering: How to Build Reliable AI Agents  
**作者/来源：** Aryan Kargwal（PhD, PolyMTL）· Arize AI  
**链接：** https://arize.com/resources/harness-engineering/  
**时间：** 更新 2026-08-18 · 抓取 2026-09-12

**原文关键段落**
> Harness engineering makes model-driven execution dependable by moving authority, state, side effects, and proof of completion into deterministic runtime controls. The model can still choose how to solve the task, but it cannot expand its own permissions, trust stale recovery state, or declare success without current evidence. … An agent spends 20 minutes changing a codebase, runs its tests, and then its worker dies before delivery. When it restarts, should it continue, rerun the tests, repeat the last action, or start over? Without a harness that can prove what state survived, every option carries risk. … A convincing final message is not evidence. The harness should inspect the current test reports, current diff, current workspace version, required approvals, and any relevant external state.

**翻译**
> Harness engineering 让模型驱动的执行变得可依赖：把权限、状态、副作用与「完成证明」挪进确定性运行时控制。模型仍可自由选路，但不能自行扩权、不能信任过期恢复态、不能用一句漂亮总结宣告成功。……Agent 改了二十分钟代码、跑完测试，交付前 worker 挂了。重启时该继续、重跑测试、重复上一步，还是推倒重来？没有能证明「什么状态还活着」的 harness，每条路都有风险。……一句有说服力的收尾不等于证据。Harness 应检查**当前**测试报告、diff、工作区版本、必要审批与相关外部状态。

**问题背景**  
一旦运行时可调工具、持状态、能 loop，难问题就变成运营题：授权了什么、允许哪些副作用、什么证据证明完成、重启后信什么、结果不明时怎么办。模型不该替自己回答这些问题。

**核心论点与论证脉络**
1. **术语分层**：Prompt 管「模型试什么」；Agent harness 管执行基底；**Harness engineering for reliability** 管合同 / 边界 / 完成门 / 持久态 / 恢复——定义执行信封，而不是规定轨迹。  
2. **六种可靠性属性**：Contracted / Bounded / Governed / Verifiable / Resumable / Recoverable。  
3. **先写任务合同**：outcome、allowed/forbidden scope、invariants、budgets、completion_gates、escalate_when——且运行时必须能强制。  
4. **完成门按副作用设计**：代码改看指纹+测试；API 写看幂等键/操作 ID + 读回；业务流看审批与源记录。  
5. **发现 vs 权威**：模糊证据交给模型；权限、schema、完成门交给代码/策略。  
6. **检查点绑证据来源**：指纹 HEAD + index + unstaged/untracked 内容哈希 + 验证产物哈希 + schema 版本。  
7. **恢复按操作类**：只读可重试；幂等写复用键并读回；结果不明先和解；不可逆需新审批。  
8. **改 harness 要当生产变更测**：单列硬门违反率、假完成率、过期 resume 接受率、重复副作用率。

**方法/架构要点**
- 控制环：合同 → 授权执行 → 记录验证态 → 完成门对照当前态 → 按副作用类恢复。  
- MCP / Skills / CLI 都是能力面；暴露、校验、授权、执行、记录仍是 harness 职责。

**可落地启示**
- 给一个真实任务写一页合同 + 2–3 条完成门（对照磁盘当前证据）。  
- 拒绝「Git status 标签当指纹」。  
- 「它说做完了」→ 问哪扇完成门对着**当前**工作区为真？

**与其他层关系**  
落在 harness 可靠性控制面；完成门服务 loop 验证环。相对昨日 Google 行为评测偏迭代断言；本文偏生产中断后仍可信。

**评价/局限**  
密度高，有可运行样例；文末有产品入口可剥离。示例偏编码 agent。

## 2. Harness · 定义解剖：从「模型缺什么」反推 harness 部件

**标题：** The Anatomy of an Agent Harness  
**作者/来源：** Vivek Trivedy · LangChain Blog  
**链接：** https://www.langchain.com/blog/the-anatomy-of-an-agent-harness  
**时间：** 发表 2026-03-10 · 抓取 2026-09-12

**原文关键段落**
> Agent = Model + Harness. If you're not the model, you're the harness. A harness is every piece of code, configuration, and execution logic that isn't the model itself. … Behavior we want (or want to fix) → Harness Design to help the model achieve this. … Harnesses today are largely delivery mechanisms for good context engineering. … In a previous blog, we showed how we improved our coding agent Top 30 to Top 5 on Terminal Bench 2.0 by only changing the harness.

**翻译**
> Agent = 模型 + Harness。你若不是模型，你就是 harness。Harness 是除模型以外的一切。……想要的行为 → 据此设计 harness。……今天的 harness 很大程度上是好的上下文工程的投递机制。……仅改 harness，编码 agent 就能从 Terminal Bench 2.0 前 30 挤进前 5。

**问题背景**  
「harness」一词被到处用却缺干净边界。作者从模型原生不能做什么出发，反推每一块为何存在。

**核心论点与论证脉络**
1. **边界测试**：不是模型的，就归 harness。  
2. **按行为反推**：filesystem、bash/code exec、sandbox、memory、compaction/skills、Ralph Loop + 验证 hooks。  
3. **训练–harness 共进化**：同模型不同 harness 榜单可差很多。  
4. **展望**：部分脚手架会被模型吸收；环境、工具、持久态、验证环仍有价值。

**可落地启示**
- 排障先问：缺能力，还是 harness 没接到模型眼前？  
- 换模型时稳住 harness；换 harness 时稳住模型与任务集。

**与其他层关系**  
定义 harness；Ralph/验证 hooks 上接 loop。相对 Arize：这边是部件从哪来，那边是如何强制可靠。

**评价/局限**  
定义清晰；日期较早；自然导向 LangChain。

## 3. Graph · 超越单环：协调系统、六个缺口、何时真该建图

**标题：** Graph Engineering, Explained: Why AI Agent Systems Are Moving Beyond One Loop  
**作者/来源：** V12 Labs  
**链接：** https://www.v12labs.io/blog/2026-08-17-graph-engineering-explained  
**时间：** 更新 2026-08 · 抓取 2026-09-12

**原文关键段落**
> Graph engineering is the practice of explicitly designing how agents, tools, deterministic code, validators, data, and humans connect to complete a task. … The important shift is not from loops to graphs. A useful agent graph contains loops. The shift is from engineering one autonomous worker to engineering the coordination system around many kinds of work. … Keep the architecture. Be skeptical of the obituary for loops.

**翻译**
> Graph engineering 是显式设计 agent、工具、确定性代码、校验器、数据与人如何连接以完成任务。……真正的转变不是从环到图。有用的 agent 图里包含环。转变是从工程化一个自治工人，到工程化协调系统。……保留架构，对「环已死」保持怀疑。

**问题背景**  
标签比定义跑得快：工作流、多 agent 组织、知识图谱都被塞进同一词。

**核心论点与论证脉络**
1. 词汇表：Node / Edge / State / Router / Fan-out·Fan-in / Gate / Cycle / Termination。  
2. 图不取代环；也不是 GraphRAG。  
3. 单环给不了：条件路由、并行 join、独立验证门、人审路径、差异化恢复。  
4. 六个缺口：示意图当架构、更多 agent=更多能力、状态无合同、handoff 欠契约、终止缺位、动图未校验。  
5. 有真实分支结构再上图；最好的图往往比第一张草图小。

**可落地启示**
- 假边审计；上图前先写终止与 merge；模型提议拓扑先确定性校验。

**与其他层关系**  
相对 Sangam 补缺口清单与成本实证；相对 Hanako 教系统何时成图。

**评价/局限**  
对炒作清醒；实现代码少。

## 4. Loop × Harness · 诊断：坏决策还是坏执行

**标题：** Loop Engineering vs Harness Engineering: What's the Difference?  
**作者/来源：** FutureAGI Blog  
**链接：** https://futureagi.com/blog/loop-engineering/loop-engineering-vs-harness-engineering/  
**时间：** 发表 2026-07-21 · 抓取 2026-09-12

**原文关键段落**
> Loop engineering sits one floor above the harness. … “What should happen next” is loop engineering. “How does this attempt actually run” is harness engineering. … If the sentence is “it tried the right thing and could not execute it cleanly,” that is a harness gap. If the sentence is “it kept repeating itself and would not stop, or it would not start without me,” that is a loop gap.

**翻译**
> Loop 在 harness 上一层。……「下一步该怎样」是 loop；「这一次怎么实际跑」是 harness。……「方向对但执行不干净」→ harness 缺口；「停不下来 / 没人催就不启动」→ loop 缺口。

**问题背景**  
「再加几次重试」常修错层。

**核心论点与论证脉络**
1. Loop = 选任务/重试/停/升级；Harness = 工具/沙箱/上下文/权限。  
2. 停条件依赖 harness 回传信号——先查信号是否准。  
3. 两层都要投，互不替代。

**可落地启示**
- 一句归因句选层再改。  
- 加 retry 前问：信号错还是规则错？

**与其他层关系**  
把 Addy 与 Vivek 收成排障清单；与 Arize 互补。

**评价/局限**  
短清晰；原创实验少。
