## 1. Harness · 生产可靠性：合同、完成门、指纹检查点与按副作用恢复

**标题：** Harness Engineering: How to Build Reliable AI Agents  
**作者/来源：** Aryan Kargwal（PhD, PolyMTL）· Arize AI  
**链接：** https://arize.com/resources/harness-engineering/  
**时间：** 更新 2026-08-18 · 抓取 2026-09-12

**原文关键段落**
> Harness engineering makes model-driven execution dependable by moving authority, state, side effects, and proof of completion into deterministic runtime controls. The model can still choose how to solve the task, but it cannot expand its own permissions, trust stale recovery state, or declare success without current evidence. … An agent spends 20 minutes changing a codebase, runs its tests, and then its worker dies before delivery. When it restarts, should it continue, rerun the tests, repeat the last action, or start over? Without a harness that can prove what state survived, every option carries risk. … A convincing final message is not evidence. The harness should inspect the current test reports, current diff, current workspace version, required approvals, and any relevant external state.

**翻译**
> Harness engineering 让模型驱动的执行变得可依赖：把权限、状态、副作用与「完成证明」挪进确定性运行时控制。模型仍可自由选路，但不能自行扩权、不能信任过期恢复态、不能用一句漂亮总结宣告成功。……Agent 改了二十分钟代码、跑完测试，交付前 worker 挂了。重启时该继续、重跑测试、重复上一步，还是推倒重来？没有能证明「什么状态还活着」的 harness，每条路都有风险。……一句有说服力的收尾不等于证据。Harness 应检查**当前**测试报告、diff、工作区版本、必要审批与相关外部状态。

**问题背景**  
一旦运行时可调工具、持状态、能 loop，难问题就变成运营题：授权了什么、允许哪些副作用、什么证据证明完成、重启后信什么、结果不明时怎么办。模型不该替自己回答这些问题。

**核心论点与论证脉络**
1. **术语分层**：Prompt 管「模型试什么」；Agent harness 管执行基底；**Harness engineering for reliability** 管合同 / 边界 / 完成门 / 持久态 / 恢复——定义执行信封，而不是规定轨迹。  
2. **六种可靠性属性**：Contracted / Bounded / Governed / Verifiable / Resumable / Recoverable。  
3. **先写任务合同**：outcome、allowed/forbidden scope、invariants、budgets、completion_gates、escalate_when——且运行时必须能强制（scope validator、预算耗尽停跑、升级进定义态）。  
4. **完成门按副作用设计**：代码改看指纹+测试；API 写看幂等键/操作 ID + 读回；业务流看审批与源记录；研究产物看 claim→source。不要把「exactly once」当通用口号。  
5. **发现 vs 权威**：模糊证据交给模型；权限、schema、完成门、精确计算交给代码/策略。保证类控制（授权、证据、幂等、和解）应随模型变强仍留着；仅为补模型弱点的脚手架应可拆。  
6. **检查点绑证据来源**：仅 commit ID 不够——要指纹 HEAD + index + 真实 unstaged 内容 + untracked 内容哈希 + 验证产物哈希 + schema 版本；工作区一变，旧「测试通过」作废。给出可运行的 Python 指纹/原子写检查点示例。  
7. **恢复按操作类**：只读可退避重试；幂等写复用同一键并读回；结果不明先和解再写；不可逆需新审批；确定性校验失败勿原样重试。  
8. **改 harness 要当生产变更测**：任务成功率之外单列硬门违反率、假完成率、过期 resume 接受率、重复副作用率；提升任务分却放宽权限/证据标准 ≠ 更可靠。

**方法/架构要点**
- 控制环：合同 → 授权执行 → 记录验证态 → 完成门对照当前态 → 按副作用类恢复。  
- MCP / Skills / CLI 都是能力面；暴露、校验、授权、执行、记录仍是 harness 职责。文中 500-run 基准提醒：按任务形状选接口，别宣称某一面万能。  
- 流水线 / 有界工作流 / agent harness 选型表：路径可预先说清就别硬上 agent loop。

**可落地启示**
- 今天下午就能做：给一个真实任务写一页合同 + 2–3 条完成门（对照磁盘上的当前证据，不对照模型自白）。  
- 检查点：拒绝「Git status 标签当指纹」；改过文件内容却仍显示 `M` 时，旧测试结果必须作废。  
- 排障句式：「它说做完了」→ 问哪扇完成门对着**当前**工作区为真？

**与其他层关系**  
落在 **harness 可靠性控制面**；完成门与独立证据直接服务 **loop 第 2 环（验证）**；按副作用恢复是长跑 loop 的硬前提。相对昨日 Google 行为评测：那边偏「迭代时行为断言」；本文偏「生产中断/不明写后仍可信」。相对 monday「走流程」护栏：Arize 把检查点指纹与假完成度量写得更工程化。相对 Field Guide / Yarchi：补上「重启后信什么」这一章。

**评价/局限**  
密度极高，几乎是生产 checklist + 可运行样例；文末有 Phoenix/AX 产品入口，读控制清单时自行剥离。示例偏编码 agent，但表格已泛化到 API/业务流/研究产物。fingerprint 样例刻意单 writer——并发同 worktree 需另加隔离/锁。

## 2. Harness · 定义解剖：从「模型缺什么」反推 harness 部件

**标题：** The Anatomy of an Agent Harness  
**作者/来源：** Vivek Trivedy · LangChain Blog  
**链接：** https://www.langchain.com/blog/the-anatomy-of-an-agent-harness  
**时间：** 发表 2026-03-10 · 抓取 2026-09-12（近几日 digests 多次引用「Agent = Model + Harness」公式，尚未整篇展开）

**原文关键段落**
> Agent = Model + Harness. If you're not the model, you're the harness. A harness is every piece of code, configuration, and execution logic that isn't the model itself. … Behavior we want (or want to fix) → Harness Design to help the model achieve this. … Harnesses today are largely delivery mechanisms for good context engineering. … Today's agent products like Claude Code and Codex are post-trained with models and harnesses in the loop. … In a previous blog, we showed how we improved our coding agent Top 30 to Top 5 on Terminal Bench 2.0 by only changing the harness.

**翻译**
> Agent = 模型 + Harness。你若不是模型，你就是 harness。Harness 是除模型以外的一切代码、配置与执行逻辑。……想要的行为（或要修的失败）→ 据此设计 harness。……今天的 harness 很大程度上是好的上下文工程的投递机制。……Claude Code / Codex 一类产品是模型与 harness 一起后训练的。……仅改 harness，编码 agent 就能从 Terminal Bench 2.0 的前 30 挤进前 5。

**问题背景**  
「harness」一词被到处用却缺干净边界。作者从模型原生不能做什么出发，反推每一块 harness 为何存在。

**核心论点与论证脉络**
1. **边界测试**：不是模型的，就归 harness——system prompt、tools/skills/MCP、文件系统与沙箱、编排（subagent/handoff/路由）、hooks/middleware。  
2. **按行为反推部件**：
   - 要持久与协作 → 文件系统（+ git）作一等原语；  
   - 要自主解题且不预置所有工具 → bash/code exec 作通用工具；  
   - 要安全与可扩缩 → sandbox + 默认工具链（测试/浏览器/日志）；  
   - 要跨会话学习与过期知识 → memory 文件标准 + web/MCP；  
   - 要抗 context rot → compaction、工具输出 offload、skills 渐进披露；  
   - 要长程自治 → Ralph Loop（拦退出、干净窗口重注目标）、计划文件、自验证 hooks。  
3. **训练–harness 共进化**：有用原语进 harness → 进下一轮后训练；副作用是换工具语义会掉分（如 apply_patch）。但「模型训练用的 harness」≠「你任务上的最佳 harness」——同模型不同 harness 榜单可差很多。  
4. **展望**：部分脚手架会被模型吸收；环境、工具、持久态、验证环仍让任意模型更有效。开放题：百级并行、自改 harness、按任务即时组装工具与上下文。

**方法/架构要点**
- 推导模式固定：Desired behavior → Harness feature。  
- Filesystem 被反复当作其他能力的底座（memory、Ralph、多 agent 协作账本）。  
- Middleware/hooks = 把确定性步骤贴进概率 loop（与姊妹文 *How Middleware Lets You Customize Your Agent Harness* 同栈）。

**可落地启示**
- 排障先问：失败是缺能力，还是 harness 没把能力接到模型眼前？  
- 长跑优先落盘计划与验证 hooks，再谈更聪明的单轮 prompt。  
- 换模型时尽量稳住 harness；换 harness 时稳住模型与任务集——别一次改两样却归因不清（与 Arize「分开实验」同构）。

**与其他层关系**  
定义 **harness 是什么**；Ralph / 验证 hooks 上接 **loop**；subagent 编排轻触 **graph**，但本文停在单 agent 系统解剖学。相对 Vinayak 学科综述：更短、更「从模型视角推导」。相对 Arize：这边是部件从哪来，那边是部件如何强制可靠。

**评价/局限**  
定义与推导清晰，适合团队对齐词汇；日期较早（3 月），未纳入 8–9 月源码论文与 Procedural Graph。自然导向 LangChain / deepagents，读「部件清单」即可，不必买栈。

## 3. Graph · 超越单环：协调系统、六个缺口、何时真该建图

**标题：** Graph Engineering, Explained: Why AI Agent Systems Are Moving Beyond One Loop  
**作者/来源：** V12 Labs  
**链接：** https://www.v12labs.io/blog/2026-08-17-graph-engineering-explained  
**时间：** 更新 2026-08 · 抓取 2026-09-12

**原文关键段落**
> Graph engineering is the practice of explicitly designing how agents, tools, deterministic code, validators, data, and humans connect to complete a task. Nodes do work. Edges decide what can happen next. Shared state carries evidence between steps. … The important shift is not from loops to graphs. A useful agent graph contains loops. The shift is from engineering one autonomous worker to engineering the coordination system around many kinds of work. … A loop asks, "Should this worker continue?" A graph asks, "Which worker or control should run next, with what state, and under which conditions?" … Keep the architecture. Be skeptical of the obituary for loops.

**翻译**
> Graph engineering 是显式设计 agent、工具、确定性代码、校验器、数据与人如何连接以完成任务。节点干活；边决定下一步；共享状态在步骤间搬运证据。……真正的转变不是「从环到图」。有用的 agent 图里**包含**环。转变是：从工程化一个自治工人，到工程化多种工作周围的协调系统。……环问「这个工人要不要继续？」图问「下一个该谁跑、带什么状态、在什么条件下？」……保留架构，对「环已死」的讣告保持怀疑。

**问题背景**  
Steinberger 一句「还在谈 loops 还是已经到 graphs？」之后，标签比定义跑得快：工作流、多 agent 组织、知识图谱、任务依赖图都被塞进同一词。需要把「真货 / 改名编排 / 何时值得」分开。

**核心论点与论证脉络**
1. **词汇表**：Node / Edge / State / Router / Fan-out·Fan-in / Gate / Cycle / Termination——与 LangGraph、AutoGen GraphFlow、Google ADK、OpenAI Agents SDK 的显式化同向。  
2. **为何现在**：单环够用后瓶颈外移；框架把拓扑变成可检对象；多 agent 失败研究（1600+ traces）显示拓扑与通信协议本身是失败源。  
3. **图不取代环**：研究/构建/评审/恢复都可以是节点内 loop；图管系统级协调。也明确：**不是** GraphRAG / GNN。  
4. **单环给不了的**：条件路由、并行+显式 join、独立验证门、人审作正常路径、按失败类隔离恢复。Anthropic 研究系统作并行案例，同时警告：多 agent 可吃约 15× token，紧耦合上下文或强依赖任务不适合。  
5. **六个覆盖缺口**（对当下「图工程内容」的批评）：把示意图当架构；更多 agent = 更多能力；共享状态当「记忆」而非数据合同；handoff 欠契约；终止语义缺位；动态造图超前于图校验（WorFBench：序列规划 ≠ 图规划）。  
6. **何时建 / 何时别建**：有真实分流、可并行合并、要审批门、要差异化恢复、要跨等待 resume、要中间态可检 → 图；短线性、同上下文、最终确定性检查够用 → 单环或函数管道。最好的图往往比第一张草图小。

**方法/架构要点**
- 每个节点：单一职责、最小可读态、结构化写出、权限与预算、成功证据。  
- 每条边：触发条件、搬运物、模型决 vs 代码决、拒收路径、可追踪。  
- 全图：共享态单一事实源、合并规则、成功/失败/升级/取消、最大 cycle 与总预算、审批边界、checkpoint/replay。

**可落地启示**
- 先对现有链做「假边」审计（下一步是否真读上一步输出）——与 seeco / Hanako 同刀，本文把它放进更大选型框架。  
- 上图前先写终止与 merge 规则；没有终止语义的图只是更精致的永不停止。  
- 模型若提议拓扑：先确定性校验可达性、环、权限、必过门、预算与合法终态，再执行。

**与其他层关系**  
相对昨日 Sangam（作者时 vs 推理时路由）：本文补「缺口清单 + Anthropic 成本实证 + 校验动态图」。相对 Sep 8 LangGraph 三年文：同「何时退回 harness」立场，但更厂商中立。相对 Hanako：Hanako 教节点内 loop / 学习边；V12 教系统何时值得成图。Harness 仍是节点内前提。

**评价/局限**  
目前公开网上对「图工程炒作」最清醒的长文之一；引用面广。深度实现代码少，落地仍要回到具体编排运行时。文末方向（可执行规格、拓扑级评测、有界自适应、耐久性）偏前瞻。

## 4. Loop × Harness · 诊断：坏决策还是坏执行

**标题：** Loop Engineering vs Harness Engineering: What's the Difference?  
**作者/来源：** FutureAGI Blog  
**链接：** https://futureagi.com/blog/loop-engineering/loop-engineering-vs-harness-engineering/  
**时间：** 发表 2026-07-21 · 抓取 2026-09-12（近几日已深写 Addy 五件套，本文作**对照诊断**补篇，不重复五原语展开）

**原文关键段落**
> Loop engineering, in Addy Osmani’s phrasing, sits one floor above the harness: it is where you replace yourself as the person prompting the agent, through the retry policy, stop condition, and step budget that decide what happens next. Harness engineering is the execution layer below it, the tools, sandbox, and context assembly that carry an action out. … “What should happen next” is loop engineering. “How does this attempt actually run” is harness engineering. … A loop with no harness underneath it has nothing reliable to decide about. A harness with no loop around it can only do one job once, then stop. … If the sentence is “it tried the right thing and could not execute it cleanly,” that is a harness gap. If the sentence is “it kept repeating itself and would not stop, or it would not start without me,” that is a loop gap.

**翻译**
> 用 Addy 的说法，loop engineering 在 harness 上一层：用重试策略、停条件、步数预算替你决定下一步。Harness engineering 是下面的执行层：工具、沙箱、上下文组装，把一次动作真正跑出去。……「下一步该怎样」是 loop；「这一次尝试怎么实际跑」是 harness。……没有可靠 harness 的 loop 无物可决；没有 loop 的 harness 只能干一次就停。……若坏跑的一句话是「方向对但执行不干净」→ harness 缺口；若是「停不下来 / 没人催就不启动」→ loop 缺口。

**问题背景**  
团队常把「再加几次重试」当万能药：有时修好，有时毫无用处——因为修错了层。

**核心论点与论证脉络**
1. **一层一问**：Loop = 选任务 / 重试 / 停 / 升级；Harness = 工具面 / 沙箱 / 上下文 / 权限 / 日志。  
2. **同一步拆两层**：队列选出失败测试（loop）→ 沙箱改代码跑测（harness）→ 再决定重试/升级/下一题（loop）。  
3. **模糊带**：停条件依赖 harness 回传信号；坏上下文会让 loop「看起来」决策很蠢；步数预算需要 harness 计量。先查信号是否准，再怪决策层。  
4. **组织债**：调度负责人与工具集成负责人常不是同一人，坏跑会卡在两层之间无人认领。

**方法/架构要点**

| | Loop | Harness |
|---|---|---|
| 层 | 决策 | 执行 |
| 典型积木 | 重试、停条件、预算、任务队列 | 工具 schema、沙箱、上下文、权限 |
| 典型坏法 | 永不停止 / 无人催不动 | 方向对但执行不安全或不干净 |

**可落地启示**
- 站会只用一句归因句选层，再改那一层。  
- 加 retry 前先问：上一次失败是信号错了，还是决策规则错了？  
- 两层都要投；只投 loop = 更自信地重试不可靠工作；只投 harness = 一次干净跑完后没人调度。

**与其他层关系**  
把 Sep 10 Addy（五原语）与 Vivek 公式收成**可操作的排障清单**；不展开 graph，但「要不要并行再开一个实例」仍标在 loop 侧。与 Arize 互补：FutureAGI 帮你选层，Arize 告诉你 harness 层要钉哪些控制。

**评价/局限**  
短、清晰、适合对齐跨职能团队；深度与原创实验少，本质是对 Addy + Vivek 的教学整理。文末有 FutureAGI 相关阅读导流。
