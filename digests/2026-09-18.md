## 1. Harness · 企业 OS：Specs / Constitution / Control Panel / Context Hub / Quality Gates

**标题：** Harness Engineering: How to Scale Agentic AI Safely（副题：The Operating System for Agentic AI）  
**作者/来源：** Aparna Kapoor, Vincent Paca, Nerijus Zemgulys · BCG  
**链接：** https://www.bcg.com/publications/2026/harness-engineering-scale-agentic-ai  
**时间：** 发表 2026-09-16 · 约 8 分钟阅读 · 抓取 2026-09-18（近五日 digests 未覆盖；今日 X 仍在转「模型商品化 → 护城河在 harness」）

**原文关键段落**
> Agentic AI holds the promise of automating the most complex business activities… Yet the reality is that AI agents are hallucinating and introducing errors into workflows, they are declaring activities finished that aren’t, or otherwise failing customer and regulatory scrutiny. … We believe the answer is to build an operating system, or harness, around agents. This process, called harness engineering, establishes and ensures effective governance, accountability, and proper controls. … As AI models become increasingly commoditized, winning with AI won’t depend on having the best model. It will depend on building an effective harness––one that captures a company’s specific processes, ways of working, and requirements. … There are five key elements that are needed for an effective harness, or agentic operating system: Specs … Constitution … Control Panel … Context Hub … Quality Gates. … We’ve found that harness engineering works best when there are four distinct types of quality gate: automated gates … evaluation gates where specialized critic agents evaluate worker agents; human stage gates where a named individual enables the system to mark a given activity as complete; and regulatory gates … Companies are increasingly buying or renting off-the-shelf AI models. But it is through the harness that a company’s own context, process logic, quality signals, governance requirements, and institutional knowledge start to matter.

**翻译**
> Agentic AI 承诺能自动化最复杂的业务活动……但现实是 agent 在幻觉、把错误写进工作流、**宣称完成其实没完成**，或过不了客户与监管审视。……我们认为答案是在 agent 周围建一套操作系统——也就是 harness。这个过程叫 harness engineering，用来建立有效的治理、问责与控制。……随着模型日益商品化，赢 AI 不再取决于拥有最好的模型，而取决于建出有效 harness——它要捕获公司特有的流程、工作方式与要求。……有效 harness（agentic OS）需要五块：Specs、Constitution、Control Panel、Context Hub、Quality Gates。……我们发现 harness 最好把质量门拆成四类：自动化门；由专门 critic agent 评 worker 的评价门；由**具名个人**放行完成的人门；以及监管门。……公司越来越多买/租现成模型；但正是通过 harness，公司自己的上下文、流程逻辑、质量信号、治理要求与制度知识才开始起作用。

**问题背景**  
大型企业多数尚未真正规模化 agent；已上线的也常报「对利润贡献有限」。假完成、幻觉、问责空洞与监管从「原则指导」转向「架构要求」同时加压。咨询语境需要一张能对 CEO/CIO 说话的 OS 隐喻，并把「护城河在模型」改写成「护城河在可定制 harness」。

**核心论点与论证脉络**
1. **PC OS 隐喻**：应用危险时由 OS 管边界；agent 同理——信任来自 harness，而不是来自模型自白。人监督仍是要素。
2. **银行案例收据**：东南亚大行财富顾问平台——顾问「主动触达客户」时间约 ×3；财富顾问收入产能 +30%+；客户转化约 4–5×；工程效率约 ×5；设计到部署速度约 +50%。作者强调增益**更多来自评价/审批/行为护栏**，而非所选模型。
3. **组织重置**：人从「做事」迁到「定目标与边界 + 关键检查点介入」；常规门可自动化（含 critic agent），关键门具名问责。银行经验：传统「大量初级底座」的人力金字塔会被压缩，设计/策略角色权重上升。
4. **五件套**：
   - **Specs**：机器可测的范围合同（目的、允许做什么/怎么做、核心评测）≈ 应用清单；
   - **Constitution**：必须做 / 必须不做 / 何时升级 / 谁问责——**确定性代码**，不可商量 ≈ 内核；
   - **Control Panel**：可见做了什么、审计、升级矩阵、失败恢复 ≈ 进程管理器；
   - **Context Hub**：私有上下文仓，防「缺信息就自信猜 / 乱上网」≈ 共享内存；这是相对对手的差异化；
   - **Quality Gates**：自动化 / critic 评价 / 具名人门 / 监管——**不要把所有检查当同一种门**。
5. **成熟度阶梯**：按风险降级审批强度（客户投资建议 = 每条人批；内部草稿 = 抽查）；信任上升后从「全检」降到「抽检」。
6. **怎么开始**：Start small；**Build, don’t buy**（通用 harness 平台买得到，制度知识买不到）；Be selective（文档清楚、质量可检、能接现有工具的流程优先）。

**方法/架构要点**
- 监管行业（金融、电信）因标准文档化，特别适合「带 harness 的 agent」；软件交付 / 规格撰写等非强监管场景同样受益。
- 从「助手贴在旧流程上」迁到「agentic-native」：某软件公司全生命周期上 harness 后团队产能自称可达约 ×5。
- 治理框架从 Day 1 进 harness，而不是事后补审计。

**可落地启示**
- 今天下午：把现有完成门拆成四列——代码自动化 / critic / 具名人 / 合规——标出「现在全挤在模型说 Done」的缺口。
- 给一条高风险工作流写一页 Constitution：永远禁止的动作、必须升级的事件、具名 owner。
- 采购话术：模型可租；Context Hub + 质量信号不可租——别把预算全砸在 frontier 模型。

**与其他层关系**  
企业叙事版 **harness**；Quality Gates 与 Tejas verify / Konishi 完成谓词同轴；Constitution 的确定性内核接 Kamau「规则进 harness」；Context Hub 接昨日 AWS 写门与 LangChain「memory = harness」。相对 DarwinX：那边用基准验证器演化 skills；这边用组织成熟度阶梯决定**谁可以放宽人门**。相对 FrankX 控制图：BCG 的四类 Quality Gate 是控制图在董事会语言里的投影。

**评价/局限**  
目前把「harness = 企业 OS」讲给非工程高管最完整的公开稿之一；有银行与软件公司量级数字。咨询体：案例不可独立复现，×3/×5 等为 BCG 客户结果陈述。Build-don’t-buy 是立场而非普适定律——初创仍可能从托管 harness 起步，再把制度知识沉进去。日期 9/16，恰落在近五日未覆盖窗口。

## 2. Graph · 控制权易手：模型只管判断，图决定下一步；先手跑再自动化

**标题：** Graph Engineering for AI Agents: From Prompts and Loops to Workflows  
**作者/来源：** Nhu Hoang · Towards Data Science（同源亦见于 Zovi AI）  
**链接：** https://towardsdatascience.com/graph-engineering-for-ai-agents-from-prompts-and-loops-to-workflows/ · https://zoviai.com/graph-engineering-for-ai-agents-from-prompts-and-loops-to-workflows/  
**时间：** 发表 2026-09-14 · 约 17 分钟 · 抓取 2026-09-18（近五日 digests 未整篇展开；昨日 FrankX / ShipWithAI 偏合同与假边，本文偏可跟做入门）

**原文关键段落**
> Prompt engineering optimizes what you say to a model. Context engineering optimizes what the model can see when it answers. Both still operate within a single turn. Loop engineering moves up a level. It gives the model tools, memory, and the ability to iterate—but control still lives inside one continuous run. The model decides what happens next. Graph engineering changes who is in control. Instead of letting the model manage the process as it goes, you define the nodes, routing logic, and checkpoints in advance. The model contributes judgment only at the steps that actually require it; the graph decides what happens next. … Don’t give the model control over the entire workflow. Give it one clearly defined step at a time. … Knowledge graphs connect information. Agent graphs coordinate work. … The goal isn’t to build the biggest graph you can draw. It’s to build the smallest one that does 4 things well: cuts real latency, keeps the checker separate from the doer, puts a human in the loop where mistakes actually carry a cost, and knows when to stop. … If it isn’t visibly better than a one-shot answer, don’t automate it.

**翻译**
> Prompt engineering 优化你对模型说什么。Context engineering 优化模型回答时能看见什么。两者仍在单轮内。Loop engineering 再升一级：给工具、记忆、迭代能力——但控制仍活在一次连续 run 里，**下一步由模型决定**。Graph engineering 改变的是**谁掌控制权**：你预先定义节点、路由与检查点；模型只在真正需要判断的步骤贡献判断，**下一步由图形决定**。……别把整条工作流的控制权交给模型；一次只给它一个清楚步骤。……知识图谱连接信息；agent 图协调工作。……目标不是画得出的最大图，而是最小却能做好四件事的图：真砍延迟、检查者与执行者分离、在错误有代价处加人、知道何时停。……若手跑并不明显好过 one-shot，就不要自动化。

**问题背景**  
Steinberger「还在谈 loop 还是已经到 graph？」与 Hamel「Loop Engineering Is Dead」引爆公开辩论后，大量读者缺一张**能本周手画**的地图。单 agent loop 的典型病：同一模型既选题、又采证、又解读、又自评信心——Shopify 簿记创业点子的「漂亮备忘录」就是假完成的亲戚。

**核心论点与论证脉络**
1. **海拔对照表**：prompt/context（单轮）→ loop（模型仍掌下一步）→ graph（结构掌下一步）。
2. **三原语**：node（LLM / 人 / 确定性代码皆可）；edge（直接 / 条件 / 并行 / 回环 / 错误 / 人控 / 事件）；state（结构化共享记录，而非无限聊天）。
3. **生产两件套**：reducer（并行写回同一字段时如何合并）；checkpoint + interrupt（崩溃恢复、等人批）。副作用节点必须幂等——否则 resume = 双发邮件。
4. **两个「graph」别焊死**：Knowledge graph（信息关系，GraphRAG）≠ Agent graph（工作如何流动）。
5. **五模式**（用同一 Shopify 图贯穿）：prompt chaining；routing（窄问题走便宜路径，低置信走宽路径）；parallelization（真独立才并行）；orchestrator-workers（工人数运行时发现，必须封顶）；evaluator-optimizer（最大轮次 +「是否还在实质改进」检测，防换皮重复）。
6. **先证明形状**：一句话输出 → 5–7 个人类会做的活 → 画依赖不画序列 → 不可逆处加人门 → **每个节点新鲜聊天、手跑一遍** → 文件化纸面痕迹 → 再选 LangGraph / AutoGen GraphFlow / n8n。

**方法/架构要点**
- 业务规则已知 → 进代码，不进「希望模型记得」。
- Routing 误分类危险：窄路径上的自信答案可能只是研究量不够——低置信默认走宽。
- Orchestrator 无上限 = 预算/限流事故；evaluator 无停滞检测 = 烧钱空转。

**可落地启示**
- 今天下午：挑一条你常用的 AI 工作流，写一句话交付物 + 最多七个岗位；手跑一轮，只问「比 one-shot 明显更好吗？」。
- 把「自检」从执行节点拆成独立 skeptic 节点——与 Tejas verify、FrankX「模型建议 ≠ 系统授权」同刀。
- 上框架前先有 `plan.md` / 各研究员文件 / `review.md`——纸面轨迹比 YAML 更早暴露假边。

**与其他层关系**  
纯 **graph** 入门施工课；明确 loop 仍是图内回环边，不是讣告。相对 ShipWithAI：那边给假边测试；本文给「先手跑」纪律与五模式菜单。相对 FrankX 三图：本文几乎只画执行图 + 一点人控边；上下文图/控制图着墨少。相对 Hanako「编排器持有一切」：orchestrator-workers 被写成有预算帽的模式，而非默认中心。相对 Colosseum：就绪门 ≈「别过早 fan-out」；本文用 routing/并行独立性表达同一直觉。

**评价/局限**  
目前公开网上把「viral 辩论 → 本周可画的 Shopify 图」讲得最跟手的长文之一；图表与边缘类型表完整。偏科普/咨询教学体，不是可跑仓库；LangGraph 选型表会过时。与 FrankX 有主题重叠，但海拔更低、可操作性更强——故今日升格为入门轴，不替代昨日合同深文。

## 3. Loop · 稳定性：重试 / 和解 / 恢复必须拆开；失败验证 ≠ 授权再改环境

**标题：** AI Agent Stability: When Retries Become the Incident  
**作者/来源：** Paul Bryant · Digital Thought Disruption（系列第 2 篇；第 1 篇验证合同，第 3 篇学习治理）  
**链接：** https://digitalthoughtdisruption.com/2026/09/12/ai-agent-stability-retries-control-loops/  
**时间：** 首发约 2026-09-12 · **Updated 2026-09-14** · 抓取 2026-09-18（近五日 digests 未覆盖；与 9/16 Konishi 同轴但更偏平台运维 / GitOps / K8s）

**原文关键段落**
> AI agent stability depends on controlling the next intervention, not simply limiting model retries. Separate repeated delivery of the same operation from reconciliation and newly authorized recovery. … A failed verification result should open a controlled recovery path, not give the agent permission to keep changing the environment until something looks healthy. … “Try again” conceals three different operations. … Transport retry … Reconciliation … Recovery action … Detecting a failed outcome does not make the next action safe. It makes the next decision necessary. … Persist an action identifier and payload digest before dispatch. Reuse the identifier only for delivery attempts with the same semantic payload. … Designate one retry owner for each remote-call boundary… Native platform reconciliation is a separate control loop, not another delivery retry to hide inside the same counter. … Create the action record and reserve its budget atomically before dispatch. … A replacement worker resumes that record rather than asking the model to reconstruct events from conversation history. … For ordinary corrective decisions, require both timing and evidence conditions. … Limit Consequences, Not Just Request Counts. … A reliable agent does not keep acting until something works. It acts only while the system can justify the next step and contain its consequences.

**翻译**
> AI agent 稳定性取决于**控制下一次干预**，而不只是限制模型重试。要把「同一操作的再次投递」与「和解」以及「新授权的恢复」分开。……验证失败应打开**受控恢复路径**，而不是授权 agent 一直改环境直到「看起来健康」。……「再试一次」掩盖了三种不同操作：传输重试、和解、恢复动作。……发现失败结果并不使下一步变安全，它只使下一步**决策**成为必要。……在 dispatch 前持久化 action id 与 payload digest；仅当语义载荷相同才复用该 id。……每个远程调用边界指定**一个**重试 owner……平台原生和解是另一条控制环，不是藏进同一计数器的又一次投递重试。……dispatch 前原子创建动作记录并预留预算；替代 worker 恢复该记录，而不是让模型从聊天史重构。……普通纠正决策要同时满足时间与证据条件。……限制的是后果，不只是请求次数。……可靠的 agent 不是一直行动到「好像好了」；它只在系统能证明下一步正当且能容纳后果时行动。

**问题背景**  
系列第 1 篇把工具成功与服务结果拆开（PASS / FAIL / PENDING / UNKNOWN）。本篇假设验证器已正确报「catalog-api 发布未过验收」——危险在于 agent 把超时当失败、把失败当「可以再改一刀」：回退请求其实已被接受、实例还在启动，agent 又要重启。K8s / GitOps / 多层客户端重试会把「我说试 3 次」变成下游 27 次。

**核心论点与论证脉络**
1. **三词表**：Transport retry（同一逻辑请求再投递）/ Reconciliation（搞清原操作是否被接受/应用）/ Recovery（因结果不可接受而改变目标——新 id、新授权）。
2. **执行门在意图与效应之间**：查当前权威、目标身份、竞争工作、剩余预算、上一操作状态；交给指定 deployment owner——agent 没有绕门的备用凭证。
3. **幂等是操作合同**：caller 提供的 id 让服务识别同意图；改参数 = 新提案。本地记 id ≠ 保证——接收方必须执行去重；模糊写无法和解时 hold 待审。
4. **重试压力全路径核算**：每层 3 次可乘成 27；指定唯一 retry owner；平台和解环不要塞进同一计数器。backoff/jitter 管时机，不管「可不可以再来一次」。
5. **持久化不确定性**：账本区分 prepared / dispatched / acknowledged / applied / verified；UNKNOWN 时阻塞依赖写。崩溃窗口：目标可能已接受但 worker 未记确认——替代者必须和解或走已验证安全重试，**不得**因丢响应就新开 id / 重置预算。需要 fencing：过期 owner 的写路径必须被拒。
6. **等效应，不等冷却**：完整服务观察窗 ≠ 投递重试秒级延迟 ≠ mutation cooldown。定时器到期只满足时间条件。
7. **一个决策一个 owner**：发布 owner 选制品；平台和解 desired state；autoscaler 管副本。GitOps 下直接改 live 而 Git 仍声明失败版本 = 假恢复。`resourceVersion` 冲突 → 重读再评估，不要为了「成功响应」去掉前置条件。
8. **限制后果**：一次 API 可滚全服务——要有 permitted-impact，不只是整数。episode = 一次批准变更及其允许恢复；告警合并进同一 episode，不另开配额。预算跨重启保留。
9. **停 ≠ 回滚**：停止应阻断新写与未授权排队；不保证已接受操作被取消。回滚有自己的有效边界（Pod 模板 ≠ schema/外部副作用）。
10. **验收测试表**：丢响应、worker 崩溃、旧 owner 复活、他方改 desired release、排队中撤权、回退验证失败——必须在真实网关/持久化/凭证/适配器上跑，不能只在对话里演。

**方法/架构要点**
- 附有 `catalog-rollout-execution-v1` 策略 YAML（非 K8s 清单）：绑定 scope、允许意图、episode 预算、transport_retry owner、verification 合同挂钩、recovery 禁止自动再提升失败版本。
- 走读：已知服务失败 → 批准兼容回退 → 新恢复意图占第二变更配额 → 丢响应 + worker 重启 → 恢复**同一**记录做只读观察 → 新完整验证窗；FAIL/UNKNOWN 走升级，禁止弹回失败版本。
- 与「更好的重试 prompt」对立：稳定性是运行时政策。

**可落地启示**
- 今天下午：给一条会写外部系统的工具路径拆三列——可安全 transport retry？如何和解？恢复是否需要新授权与新 action id？
- 审计客户端栈：有几个独立「最多 3 次」？乘起来给目标多少次？
- 把 Konishi 副作用账本与本文 execution ledger 对齐：至少要能回答 prepared vs applied vs verified。

**与其他层关系**
