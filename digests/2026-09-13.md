## 1. Harness · 十套对照：五部件、三种哲学、60 行最小环

**标题：** What Is an Agent Harness? The Architecture Behind Claude Code, DeepSeek Harness, and Hermes Agent  
**作者/来源：** Rudrendu Paul · freeCodeCamp  
**链接：** https://www.freecodecamp.org/news/what-is-an-agent-harness/  
**时间：** 发表 2026-09-11 · 抓取 2026-09-13

**原文关键段落**
> A harness is the runtime shell wrapped around an LLM model. The model itself only does one thing: given a stream of text and a list of available tools, it predicts what to say or which tool to call next. The harness handles everything else. … That five-step loop … is the part every harness on the market shares. What varies … is everything wrapped around step 3 and step 4: how good the planning is before execution starts, how the memory decides what to keep and what to drop … how isolated the sandbox is, and whether the harness can spin up a second, smaller version of itself … Without [a turn/cost limit], a harness … will keep looping and keep spending tokens … If you forget that line during a refactor, the failure looks identical from the outside: a job that never returns, and a token bill that keeps climbing …

**翻译**
> Harness 是包在 LLM 外面的运行时外壳。模型只做一件事：给定文本流与工具列表，预测下一句或下一个工具调用。其余全是 harness。……市场上的 harness 都共享那五步环。真正拉开差距的，是第 3–4 步外围：执行前规划好不好、记忆留什么扔什么、沙箱隔离多严、能否拉起干净上下文的子 agent。……没有轮次/成本上限，harness 会一直烧 token。……重构时删掉那一行，从外看症状一模一样：任务永不返回，账单持续爬升。

**问题背景**  
2026 年 DeepSeek Harness 两天冲到 9.5 万星，Pi 则用一年有机增长到相近星数——同一「harness」词，两种增长曲线与设计哲学。缺一篇把「框架 → harness」转向说清、并用同一五部件尺子量十套产品的公开长文。

**核心论点与论证脉络**
1. **定义**：Harness ≠ 2023–25 的 agent framework（你自己拼积木）；而是**已经把 loop 造好、对 memory/planning/safety 有主张**的可运行产品。Claude Code 让这一转向不可忽视；LangChain Deep Agents 则试图把 Claude Code 的四机制做成模型无关库。  
2. **共享五部件**：loop / tool router / memory / planning / sandbox——中心是模型下一 token，外围决定长会话是否可靠。  
3. **Deep Agents 四机制**（值得背下来）：planning tool、虚拟文件系统与沙箱、subagent 委派、上下文压缩/大输出 offload。作者认为「是否仍叫 Deep Agents」不重要，这四题每个认真 harness 都要答。  
4. **三种（加一种）哲学**：
   - DeepSeek：**Everything is a plugin**（Cordis）——防架构锁定；  
   - Claude Code / Deep Agents：**少量固定机制做透**——防长会话漂移；  
   - Hermes：**跨会话复利技能库**——防重复劳动，也有技能债风险；  
   - Pi / Oh-My-Pi：**极简四工具 + 扩展**——防臃肿。  
5. **选型问失败模式**：今天卡你的是锁死、长跑不可靠、跨会话重复，还是审计面过大？星数曲线形状（发射尖峰 vs 缓坡）比绝对星数更说明「六个月后是否还开着」。  
6. **栈分层**：MCP（协议）→ harness → 编排（LangGraph/CrewAI/AG2/Mastra/DSPy）→ 观测（Langfuse/LangSmith）+ 沙箱（E2B/Modal）。别用 harness 去修属于上一层或下一层的 bug。

**方法/架构要点**
- 五步环：组装 prompt → 模型提议工具 → harness 执行 → 回填结果 → 直到终答或硬停。  
- 文中给出约 60 行 Anthropic Messages API 最小 harness：`read_file` / `write_file` / `run_bash`，`cwd="./sandbox"` 与 `max_turns` 被标为承重安全边界。  
- 编码 harness 有 repo/test/diff 作工作单元；知识工作 harness 必须先问「等价于 diff 的验收物是什么」。

**可落地启示**
- 今天下午：跑通最小环，故意去掉 `max_turns` 与 `cwd` 各一次，亲眼看「永不返回」与「逃出沙箱」长什么样。  
- 选型会只问一句：我们最贵的失败模式是哪一种哲学在优化？  
- 观测从第一天起非可选——无人值守第 30 轮失败，没有 trace 就是噩梦。

**与其他层关系**  
几乎全在 **harness 产品/架构对照**；loop 以共享五步环出现；多 agent 明确上交给编排层（graph）。相对 Sep 8 Atoms「三架构中心」：本文尺子更宽（十产品 + 增长曲线 + 可运行脚手架）。相对 Sep 12 Vivek 解剖：Vivek 从「模型不能做的事」反推部件；本文用市场横截面验证同一部件清单。

**评价/局限**  
目前公开网上最好的「入门 + 选型」合集之一；表格与哲学柱清晰。部分星数/榜单会漂；文末有作者 GitHub 导流，读架构时自行剥离。对生产完成门 / 指纹检查点不如 Arize 深——应与昨日 Arize 对照读。

## 2. Graph × Loop × Harness · 云工程实证：证据门、有界恢复、零信任

**标题：** Towards Agentic Cloud Engineering: Graph and Loop Engineering with a Zero-Trust Agent Harness（论文）+ Agentic Cloud Engineering…（工程解读）  
**作者/来源：** Sakhinana & Runkana（Tata Research Development and Design Centre）· arXiv:2609.00050；解读 Daniel Vaughan · Codex Knowledge Base  
**链接：** https://arxiv.org/abs/2609.00050 · 解读 https://codex.danielvaughan.com/2026/09/06/agentic-cloud-engineering-graph-loop-zero-trust-harness-codex-cli/  
**时间：** 论文约 2026-09 · 解读发表 2026-09-06、更新 2026-09-10 · 抓取 2026-09-13（近五日 digests 未整篇展开；Sep 11 仅把 companion 采纳研究当补充线索）

**原文关键段落**
> The framework separates three complementary concerns: graph engineering specifies long-horizon workflow progression and verification-dependent transitions; loop engineering provides bounded diagnosis, repair or re-planning, retry, and re-verification; and agent harness engineering enforces zero-trust execution through identity, authorization, policy-scoped capabilities, isolation, and runtime safeguards. … Complete ⟺ RepoValid ∧ DeployVerified ∧ RuntimeVerified … Without any recovery loop, GPT-5.6 Sol drops to 12.9% [from 95.0%]. … EGER and BTR hold at 100% regardless of model — these are framework-enforced properties. … model capability determines how often you succeed; the framework determines whether failure is bounded and auditable.

**翻译**
> 框架拆成三件正交事：graph 规定长程推进与**依赖验证的转移**；loop 提供有界诊断 / 修复或重规划 / 重试 / 再验证；harness 用身份、授权、策略范围能力、隔离与运行时防护做零信任执行。……完成 = 仓库有效 ∧ 部署已验证 ∧ 运行时已验证。……拿掉恢复环后，同一模型 GPT-5.6 Sol 的已验证完成率从 95.0% 掉到 12.9%。……EGER 与 BTR 在所有模型上都是 100%——这是框架强制属性。……模型能力决定你多常成功；框架决定失败是否有界、可审计。

**问题背景**  
多数编码/云 agent 部署仍默认「强模型 + 合理 prompt 就够」。云工程任务一旦改基础设施、部署、验活，需要证明：推进是否有证据、恢复是否有预算、能力是否可绕过模型自白。

**核心论点与论证脉络**
1. **三层正交且模型无关**：证据门跑 `kubectl get pods` / 退出码，不问模型「部署成功了吗」；loop 看尝试计数器；harness 问 OPA Gatekeeper。  
2. **Graph = 证据门控状态机**：Planning → RepoValidation ↔ loop → DeployVerification ↔ loop → RuntimeVerification ↔ loop → Complete；预算耗尽 → TerminalFailure。到达失败终态与成功终态同样可审计、同样有界。  
3. **Loop 预算有牙**：每工作流最多 20 次恢复、120 分钟墙钟、10M token、500 tool calls，外加成本天花板与爆炸半径限制。500 次工具调用不是「资源紧张」，而是把无界搜索收成有界计算。恢复成功率随阶段下降：仓库校验 > 部署验证 > 运行时验证（活基础设施更难修）。  
4. **Zero-trust harness**：Workload Identity、RBAC/ABAC、OPA（进程外、模型绕不过）、按 agent 的 MCP 能力范围（无环境能力继承）、gVisor、Cilium egress allowlist、Falco 异常作可触发 loop 的证据。未授权能力拒绝率 100%；授权放行约 99.3%。  
5. **实验范围**：140 个自然语言任务 × 14 个云工程域 × 六种受控失败；VTCR 随模型变（Flash-Lite 56.4% → GPT-5.6 Sol 95.0%），但 **EGER/BTR 全员 100%**——核心主张是「成功频率归模型，有界可审计归框架」。  
6. **采纳现实（companion arXiv:2608.21884）**：36,710 仓里确认自治 loop 仅 217（0.59%），且几乎没有提交的 goal/stop/budget/state 文件——多数团队仍在跑无界环。

**方法/架构要点**
- 完成谓词三者同时为真；用模型自报完成替换机器门时，EGER 从 100% 掉到 99.0%，840 次执行中出现 4 次非法推进——生产里即「幽灵部署」。  
- Codex CLI 映射：`PostToolUse` hook 退出码 2 ≈ 证据门；`max_turns` / `rollout_budget` ≈ loop 界；sandbox writable_roots + network allowlist + approval policy ≈ harness 局部；OPA/Falco 级仍靠宿主容器。

**可落地启示**
- 今天下午：给一条真实部署路径写三个机器门（repo / deploy / runtime），禁止「模型说完成」推进状态。  
- 恢复环 ablation 数字可当立项弹药：同一模型，有界恢复 vs 无恢复可差一个数量级。  
- 对照自家仓：有没有提交的 stop/budget/state？没有就默认你在 0.59% 之外的无界多数里。

**与其他层关系**  
把 **graph（证据转移）/ loop（有界恢复）/ harness（零信任）** 收成同一云工程坐标系。相对 Sep 10 Addy 五原语与 Sep 11 loop 采纳补充：本文给出云域硬数字与 GCP 实例化。相对 Sep 12 Arize：Arize 偏通用完成门与指纹；本文偏 kubectl/OPA/gVisor 级控制面。相对 V12「何时上图」：这里图的「边」被定义成证据谓词，不是示意图。

**评价/局限**  
ablation 与「框架强制指标 vs 模型能力指标」拆分极有说服力；深度依赖解读文中的表格与论文摘要（本轮 arXiv HTML/PDF 抓取超时，数字以解读文引用为准，建议对照 PDF）。实例化偏 Google Cloud；Codex 映射是近似而非一等公民集成。

## 3. Harness · 供应链：配置层没有 lockfile

**标题：** Scanning the Harness: An Empirical Study of Supply-Chain Defects in AI Coding-Agent Configurations  
**作者/来源：** arXiv:2609.07360  
**链接：** https://arxiv.org/abs/2609.07360  
**时间：** 提交约 2026-09-07 · 今日 X 线索 @ayyazdev · 抓取 2026-09-13

**原文关键段落**
> AI coding agents such as Claude Code, Cursor, GitHub Copilot, and OpenAI Codex are configured through artifacts developers write and share: instruction files, skills, hooks, MCP server declarations, subagents. This harness is a dependency layer installed from marketplaces and public repositories, running with the developer's privileges, with no lockfile, no install-time check, and no vocabulary for what a component may do. We study it over 3,171 public GitHub repositories: 2,660 setups that assemble two or more component types and 511 published skill collections. … Three security classes survive: 9.8% of setups install an MCP server with no version pinned, 3.1% pre-approve arbitrary execution behind a scoped-looking grant such as Bash(python:*), and 3.8% carry a skill that pre-approves the shell for whoever installs it. In total 16.0% of setups carry a security defect … No credential-exfiltration path was confirmed. The instrument, corpus manifest, prompt, and every verdict are released.

**翻译**
> Claude Code / Cursor / Copilot / Codex 一类编码 agent，靠开发者编写并分享的配置工件运转：指令文件、skills、hooks、MCP 声明、subagents。这层 harness 是从市场与公开仓安装的**依赖层**，以开发者权限运行——没有 lockfile、没有安装时检查、也没有「组件允许做什么」的词汇。……研究覆盖 3,171 个公开 GitHub 仓：2,660 个多组件装配、511 个已发布 skill 合集。……三类安全缺陷存活：9.8% 安装未钉版本的 MCP；3.1% 用看起来有范围的授权（如 `Bash(python:*)`）预批准任意执行；3.8% 的 setup 携带「谁装谁就预批准 shell」的 skill。合计 16.0% 有安全缺陷。……未确认凭据外泄路径。仪器、语料清单、prompt 与每条裁决均公开。

**问题背景**  
团队已开始认真做权限网关与沙箱，却常把 MCP / skills / hooks 当成「配置文件」而非依赖。结果是：应用有 `package-lock.json`，agent 工具面却每次 `npx -y` 拉 latest。

**核心论点与论证脉络**
1. **命名问题**：harness 配置 = 供应链依赖，却缺少包管理器那套钉版本 / 完整性 / 能力声明。  
2. **度量纪律**：只计「从字节可判定、且后果是安全暴露 / 无法工作 / 偏离 Agent Skills 规范」的规则；每条命中经独立重导、双模型裁决后才计数——原始扫描 25.5%，确认后安全缺陷 16.0%、任意确认缺陷 16.7%。  
3. **三类存活缺陷**：未钉 MCP 版本；「看起来 scoped」的预批准实际等价任意执行；可分发 skill 替安装者预批准 shell（市场扫描可见，约占合集 3.7%）。  
4. **对照观察**：跨文件比较类规则多为「有意差异」，作 observation 而非缺陷。  
5. **实践修复（X 摘要与生态呼应）**：钉 MCP 版本；安装 skill 前读其 pre-approvals；进一步可用 `mcp.lock` / ToolPin 一类工具对 `tools/list` 表面做哈希门禁（mcpindex / mcpguards 等实践文）。

**方法/架构要点**
- 语料：公开仓多组件 setup + 发布 skill 合集；钉 commit 复现。  
- 验证管线：规则扫描 → 独立实现重导 → LM 裁决分歧 → 第二模型会话复核。  
- 与「prompt 注入扫描器」分工：本文把 MCP 当**软件制品**做完整性与权限预批准审计。

**可落地启示**
- 今天下午：扫一遍仓内 MCP 声明，凡 `npx -y` 无版本的打成 P0。  
- Skill 安装 checklist：先读 pre-approve / hooks，再装；把「替你点过 shell」当供应链事件。  
- CI 加 drift gate：`tools/list` 哈希或锁文件变更必须过人审（呼应 NSA/OWASP 对 MCP 钉版本与工具定义哈希的建议）。

**与其他层关系**  
落在 **harness 的依赖/权限供应链**；直接加强零信任论文里的「MCP capability scoping」。相对 Sep 12 Arize「合同与完成门」：那边管运行时证据，这边管**装进来的工具面是否仍是你审过的那一张**。Loop/graph 几乎不涉及——但无界权限会让任何 loop 的爆炸半径失控。

**评价/局限**  
问题定义漂亮（「没有 lockfile 的依赖层」），方法透明度高（仪器与裁决公开）。本轮未能完整拉取 PDF 正文，深度数字与规则表以 abs + 高信号转述为准。未确认凭据外泄 ≠ 未来没有；锁文件也防不住「第一天就批准了不该批准的东西」。

## 4. 三层海拔 · 嵌套透镜与「由内向外建」

**标题：** Loop vs Graph vs Harness Engineering: Three Lenses People Keep Confusing  
**作者/来源：** CareerStack  
**链接：** https://careerstack.dev/loop-vs-graph-vs-harness-engineering  
**时间：** 发表 2026-07-23 · 抓取 2026-09-13（近五日未深写；与 Sep 9 Paul Serban、Sep 12 FutureAGI 同轴，但投资顺序主张不同）

**原文关键段落**
> Loop engineering = how the agent iterates. Graph engineering = how you express that iteration when it branches, forks or needs to resume. Harness engineering = everything wrapped around it that makes it safe, observable and affordable. Loop is inside graph; graph is inside harness. … Build them in the order loop → harness → graph. Get a bounded loop working, wrap it in enough harness that you can trace and stop it, and only reach for a graph when the control flow genuinely branches. Most teams do it backwards — they start with an elaborate graph, then discover they can’t see inside it. A graph you can’t replay is just a prettier version of the problem you were trying to solve. … a spinning agent is a loop problem, an unreadable one is a graph problem, and an unexplainable one is a harness problem.

**翻译**
> Loop = agent 如何迭代；Graph = 分支/分叉/恢复时如何表达该迭代；Harness = 让整件事安全、可观测、可负担的外围。Loop 在 graph 里，graph 在 harness 里。……建造顺序：**loop → harness → graph**。先让有界 loop 跑起来，再包够能追踪与停住的 harness，只有控制流真分支才上图。多数团队反过来：先画华丽图，再发现看不见内部。不能回放的图，只是问题的更漂亮版本。……空转 = loop 问题；不可读 = graph 问题；不可解释 = harness 问题。

**问题背景**  
设计评审里三个词被当同义词互骂：有人把 LangGraph 状态机叫 loop engineering，有人把加一次 retry 叫 harness engineering。需要一张「海拔」图，让讨论先对齐层再吵方案。

**核心论点与论证脉络**
1. **嵌套而非竞争**：heartbeat（loop）⊂ shape of control（graph）⊂ production scaffold（harness）。  
2. **每层核心问句与标志失败**：

| 透镜 | 核心问题 | 标志失败 |
|---|---|---|
| Loop | 何时继续、何时停？ | 无界空转 |
| Graph | 如何让分支可读、可恢复？ | 仪式过度 / 或嵌套 if 不可读 |
| Harness | 如何安全、便宜、可调试？ | 无 trace、无预算、盲信工具参数 |

3. **实践切片**：编码 agent 修失败测试 = 典型 loop（含「两轮同错即 abort」）；退款路由+审批检查点 = 典型 graph；`transfer_funds` schema 校验+人审+轨迹 = 典型 harness。  
4. **建造顺序争议点**：本文主张 loop→harness→graph；Paul Serban（Sep 9）主张权限模型与外部停条件杠杆最高、graph 欠投资——两者在「别过早上复杂图」上一致，在「先有界环还是先权限网关」上可并存为：最小有界环 + 同步最小权限，再扩张。

**方法/架构要点**
- 评审话术表：聊步数/预算/停不下来 → 说 loop；聊分支/并行/checkpoint → 说 graph；聊工具安全/记忆/重试/成本/追踪 → 说 harness。  
- Founder 忠告：能回放的控制层才是 graph 的回报；图本身不是目标。

**可落地启示**
- 站会先指海拔，再改代码——与 FutureAGI「坏决策 vs 坏执行」句式同刀。
