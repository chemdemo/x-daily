## 1. Harness · 同一 prompt：六部件 + 外层 verify 环，把假完成拧成真证据

**标题：** What Is an Agent Harness? Harness Engineering Explained  
**作者/来源：** Tejas Kumar（AI Engineer, IBM）· tej.as  
**链接：** https://tej.as/blog/what-is-an-agent-harness · 代码 https://github.com/TejasQ/basically-ai-harness（每步一分支）  
**时间：** 发表 2026-09-14 · 抓取 2026-09-15（近五日 digests 未覆盖）

**原文关键段落**
> An agent harness is everything around the model that gives it grounding in reality: the tools it can call, the context it sees, the guardrails that stop it, the loop that drives it, and the checks that verify what it claims. … The harness is not the agent loop. It’s everything around the loop. … Don’t trust the loop’s exit. A model saying it’s done is a claim. Verify it in code. … I picked GPT-3.5 Turbo on purpose. If a harness can make a weak, cheap model do real work, it can make a strong one boringly reliable. And I set myself one rule: the prompt never changes. … Lesson: move secrets and fragile, deterministic steps out of the model and into the harness. … My hope for 2027 is dynamic harnesses, generated on the fly. You ask an agent to buy you a flight, and before it touches anything it builds a harness for that specific task.

**翻译**
> Agent harness 是模型周围一切让它落地现实的东西：能调的工具、看到的上下文、挡住它的护栏、驱动它的 loop、以及核验其宣称的检查。……Harness 不是 agent loop，而是 loop 周围的一切。……别信 loop 的退出条件。模型说做完了只是主张，要用代码核验。……故意选用 GPT-3.5 Turbo：若 harness 能让弱便宜模型干真活，也能让强模型无聊地可靠。自定一条规则：prompt 永不改。……启示：把秘密与脆弱的确定性步骤挪出模型、放进 harness。……对 2027 的期望是动态 harness：你让 agent 订机票，它先为该任务生成一套 harness，再动手。

**问题背景**  
租来的模型是黑箱；HN 点赞 demo 里，GPT-3.5 打开登录页却报告「已 upvote」。团队本能是改 prompt / 换模型。作者要证明：**同一 prompt、同一弱模型，只改 harness 代码**就能从假完成走到真成功——并把「evaluation harness」与「agent harness」从词汇上拆开。

**核心论点与论证脉络**
1. **定义靠职责，不靠减法**：LangChain / Birgitta 的「除模型外一切」正确，但更有用的定义是——把你控制不了的黑箱，锚到你控制得了的环境。攀岩绳 / 狗绳隐喻：护栏与 verify 像「接住坠落」；loop 与 tool registry 像「选方向」；但绳子不能替你确认到顶，所以 agent harness 还必须有核验。  
2. **六部件表**：tool registry / model / context management / guardrails / agent loop / verify step——明确回答「harness = loop 吗？」：**不是**；harness 甚至可以是 **loop 外再套一层 loop**。  
3. **五步施工（分支 0→4）**：
   - **0** 裸环：`finish_reason === "stop"` 即信 → 撞登录页仍报成功；  
   - **1** 护栏：`maxIterations` / `maxMessages` + 朴素 trim（留 system+task+尾部）——模型绕不过的硬停；  
   - **2** 抽出 `runHarness`：行为不变，给后续挂点；  
   - **3** **确定性 verify**：扫 trace 找真实 upvote 点击 / 登录页；失败理由替换模型自白；外层最多 3 次 attempt；「诚实失败」是进步；  
   - **4** harness 代登录：凭据在 env，模型永不看见密码；登录后注入「已认证，继续任务」——6 轮后真 upvote。  
4. **Harness engineering 习惯**：Hashimoto「出错就工程化到不再出错」；OpenAI / LangChain / Birgitta 同轴。Context engineering 只是其中一块。  
5. **开放题**：多少 verify 够？哪些检查必须代码、哪些可交给另一模型？动态、按任务生成 harness 仍是前瞻。

**方法/架构要点**
- Verify 读的是 **tool history / trace**，不是模型散文；登录页命中可标 `fatal: true` 避免无意义重试。  
- Guardrail 是纯函数看 run state → `{ ok, reason }`；与「礼貌请模型停下」对立。  
- 仓库一分支一步，便于对照；演示用 Playwright 真浏览器。

**可落地启示**
- 今天下午：给现有 loop 加一层「attempt → verify(trace) → retry」；完成判定从 `stop` 改为「世界证据」。  
- 把登录、支付、密钥填充等确定性脆步骤写成 harness handler，禁止进 prompt。  
- 弱模型 demo 是教学武器：错误更响 = 更容易看见缺哪块 harness（与昨日 Kamau「系统当地板」同构）。

**与其他层关系**  
纯 **harness** 施工课；外层 attempt 环是 **loop 的验证/停步** 实例化。相对 Sep 14 Kamau：同「别信自白」，本文给出可跑分支与 HN 真任务。相对 Auto-RecSys「认知–程序分离」：登录/状态写入 = 程序侧。相对 Birgitta Guides×Sensors：verify = 为 LLM 消费优化前的**计算型 sensor**；护栏 = 硬 guide。相对 Google 行为评测（已覆盖）：那边测「有没有某行为」；这边测「世界有没有某副作用」。

**评价/局限**  
目前把「假完成 → 真证据」讲得最可跟做的公开长文之一；IBM OpenRAG 安全语境一句带过，不喧宾。trim 作者自承不可上生产；动态 harness 仍是愿景。文末有 workshop 导流，读架构时剥离即可。

## 2. Loop · 三层 Feedback Loop：别只改下一次 run，改「项目被 agent 工作的条件」

**标题：** Feedback Loop Engineering: making your project agent-ready  
**作者/来源：** Maria Gorinova & Simon Maple · Tessl Blog  
**链接：** https://tessl.io/blog/feedback-loop-engineering-making-your-project-agent-ready  
**时间：** 发表 2026-09-04 · X 再推 2026-09-14（@ainativedev）· 抓取 2026-09-15（近五日 digests 未展开「middle loop / 项目可学习」这一命名）

**原文关键段落**
> We’ve started calling the bigger picture feedback loop engineering: the practice of designing the loops around your agents so that each run improves the conditions for future runs. … The inner loop operates over a single change. … The middle loop operates across the project and its history. This is where maintenance agents live. … The outer loop reads signals from production and the business. … The agent platform may be exactly the same before and after. … At Tessl we run four maintenance agents daily. Each files roughly two issues per run, and we have accumulated around 500 issues tagged as maintenance-origin. … One audit of Kikimora examined 1,102 commits, review threads from 400 merged PRs, CI runs, agent transcripts and 108 supervision sessions. It produced 63 findings, and 86% of the findings we triaged were dispatched as work. … The data sources are the whole game.

**翻译**
> 我们开始把更大图景叫 feedback loop engineering：设计 agent 周围的环，让**每一次 run 改善未来 run 的条件**。……内环覆盖单次变更。……中环覆盖项目及其历史——维护 agent 住在这里。……外环读生产与业务信号。……改完前后，agent 平台可以完全一样。……Tessl 每天跑四个维护 agent，每次各提约两个 issue，已积约 500 个 maintenance 标签 issue。……对 Kikimora 一次深审计覆盖 1,102 commits、400 个已合并 PR 的评审线程、CI、agent 转录与 108 次监督会话，产出 63 条发现，分拣后 86% 派成工作。……数据源就是整场游戏。

**问题背景**  
多数 agentic 精力花在「这一次怎么更听话」：更好 prompt / 模型 / skill / review。但同一问题可被 agent 修十次仍不学——因为学的对象错了。需要一个名字，把「改项目、让未来 agent 更省事」从「改 agent」里拎出来，并指出常缺的**中间层**。

**核心论点与论证脉络**
1. **三层按看见问题的速度分层**：
   - **Inner**：单次变更上的测试 / 类型 / lint / PR 评审——拦坏变更落地；  
   - **Middle**：跨历史的 drift loop（文档腐、测试衰、复杂度涨）与 retro loop（重复评审意见、flaky、agent 摩擦）→ 把模式变成常规流水线里的纠正工作；  
   - **Outer**：错误率 / 产品指标越阈则建单或直接响应（如重启失败服务）——检验前两环在真实系统是否成立。  
2. **中环目标是项目，不是平台**：平台可不变；目标从 agent 日志、重复 PR 评论、架构分析出发，问「项目应如何改」。agent 写码占比越高，单次变更越看不见十次变更积累的重复逻辑 / 不一致抽象 / 过期指引——中环给项目自我反思。  
3. **维护 agent 工作方式**：定时或按票启动 → 分析一小束数据 → 短报告 → **只建普通 issue，不直接开 PR** → 与人提的工作进同一管道。先手跑审 issue，信号稳再调度；小而机械的修复才逐步提高自治。  
4. **数据源决定环质量**：agent 日志（多轮空转 / 反复迷惑）→ 摩擦；重复评审与 CI → 公约太晚；仓当前态 → drift；生产遥测 → 外环。解释必须显式，否则环只会吵。  
5. **起步三件套**：好数据源 + 读懂它揭示什么 + 清晰改善目标；先窄问题（文档 drift 或重复评审），手跑一次再 schedule。

**方法/架构要点**
- 案例：retro 发现 agent 反复重推 Linear API 用法 → 做小 CLI → 之后每次 run 更稳——典型「摩擦 → 工具面沉淀」。  
- 环健康度量仍在建：噪声、发现被忽略、纠正是否真改善项目。  
- 与「只优化下一 run」对立：下一 run 优化是内环周边；feedback loop engineering 强调中/外环复利。

**可落地启示**
- 今天下午：从最近 20 条 agent 转录里标「同一困惑 ≥3 次」的主题，开一张 maintenance issue（工具 / lint / 文档三选一最便宜的耐久修复）。  
- 维护 agent 默认 **只建单、不直接合**——先证明信号，再谈自治合并。  
- 站会话术：这次失败是内环漏检，还是中环该把「重复评论」收成规则？

**与其他层关系**  
落在 **loop 的 meta 层**（改环境 / 改项目），直接服务 **harness 的耐久指南与工具面**。相对 Auto-RecSys Execution Evolution：那边结晶的是 per-model playbook；这边结晶的是仓内 lint/CLI/文档。相对 Birgitta steering loop：同「人的工作是转向 harness」，Tessl 把转向对象钉成**可调度的维护 agent + issue 管道**。相对 Nnenna meta-loop / Sep 14 补充线索：同构，本文给出规模数字与「不直接开 PR」纪律。Graph 几乎不涉及——除非维护工作本身要分支并行审计。

**评价/局限**  
命名清楚、案例具体（500 maintenance issues、86% 分拣派发）；Tessl 产品语境可感但正文原则可移植。环健康度量自承未完成；外环着墨少于中环。日期 9/4，今日因 X 再推与「中环缺席」诊断而升格。
