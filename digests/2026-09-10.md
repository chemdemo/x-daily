## 1. Graph · 程序知识外置：自演化 Procedural Graph

**标题：** Procedural Graphs: Self-Evolving Execution Structures for LLM Agents  
**作者/来源：** Yuxing Lu, Yicheng Chen, Shanchan Wu, Sercan Ö. Arık（Google / Georgia Tech / Peking University 等协作）· arXiv:2609.09153  
**链接：** https://arxiv.org/abs/2609.09153 · PDF：https://arxiv.org/pdf/2609.09153  
**时间：** 提交 2026-09-08 · 抓取 2026-09-10

**原文关键段落**
> Most agents select actions through unconstrained generation over an accumulating history, leaving implicit the procedural knowledge of what to do, in what order, and under which conditions. … We introduce the Procedural Graph: just as a knowledge graph organizes factual knowledge into (entity, relation, entity) triplets for what-is questions, a Procedural Graph organizes procedural knowledge into (procedure, relation, procedure) triplets for what-to-do questions. At each decision step, the framework localizes the agent's active node, and a guidance model translates the surrounding subgraph into step-level situational guidance that biases the solver's next action without dictating it. The graph is self-evolving: an LLM refiner contrasts failed trajectories with successful ones and edits the graph's topology and attributes, committing edits that preserve or improve held-out validation performance while retaining rejected ones to discourage repetition.

**翻译**
> 多数 agent 仍在不断累积的历史上做无约束生成，把「做什么、按什么顺序、在什么条件下做」的程序性知识留在隐式里。……我们提出 Procedural Graph：正如知识图谱用 (实体, 关系, 实体) 回答「是什么」，Procedural Graph 用 (步骤, 关系, 步骤) 回答「下一步做什么」。每一步先定位当前活跃节点，再由 guidance model 把邻接子图译成情境化指导——偏置 solver 的下一动作，但不硬编码。图可自演化：LLM refiner 对比失败与成功轨迹，编辑拓扑与属性；只提交在 held-out 验证上不降级的改动，并记住被拒改动以免重犯。

**问题背景**  
长程工具调用里，目标漂移、工具乱序、重复死胡同，根源常是「流程」只活在对话史里。记忆/知识图谱回答「世界是什么」，却不直接回答「现在该怎么走」。

**核心论点与论证脉络**
1. **知识 vs 程序**：KG 管 what-is；Procedural Graph 管 what-to-do——节点是动作/技能/任务态，边是允许转移 + 条件/坑点。  
2. **定位 → 局部检索 → 软指导**：不强迫 LLM 自己从全历史重建工作流；只把局部邻域译成 guidance，保留推理灵活度。  
3. **自演化闭环**：从最小骨架起步；refiner 改图；**验证门**决定是否 commit；被拒编辑留档防重复错误。也可修复有缺陷的专家先验。  
4. 跨多数据集、任务类型与 LLM 家族，相对 memory baseline 稳定增益；自演化无需手工工程也能继续抬分。

**方法/架构要点**
- 决策时：localize active node → retrieve neighborhood → generate situational guidance → solver acts。  
- 学习时：success/fail contrast → propose graph edits → held-out gate → accept/reject memory。  
- 与硬编码 DAG 不同：图提供结构约束，模型仍负责局部选择；与纯 ReAct 历史不同：流程是一等公民、可检查、可进化。

**可落地启示**
- 若失败模式是「半路忘目标 / 工具乱序」，先问：流程是否只存在于 transcript？  
- 任何「改工作流」的自动提案都要有 held-out 门——否则一次坏更新会固化成持久状态。  
- 与昨日 Hanako「纠错边 + 学习边」同构：这里学习边直接写回 **图拓扑**。

**与其他层关系**  
明确落在 **graph 层**（程序结构），自演化环是 **loop 第 4 环（爬山/元改进）** 的图特化；harness（工具、权限、证据）仍是执行前提。相对 LangGraph「显式先验路径」：本文更强调 **可演化的程序记忆**，而不是一次性画死的编排。

**评价/局限**  
问题定义漂亮、与 KG 对照清晰；正文 HTML 抓取超时，深度数字与消融以 PDF 为准。生产落地还要补：编辑 provenance/回滚、并发任务下的多图版本、以及与权限网关的接合。X 上 @omarsar0 等已作高信号线索（非主体）。

## 2. Harness · 六项可决策设计：先写停条件与四份文件

**标题：** How to Design an Agent Harness: six decisions that turn a model into a worker you can leave alone  
**作者/来源：** Yarchi (@undefinedKi) · X Article  
**链接：** https://x.com/undefinedKi/article/2088611136027361368  
**时间：** 发表 2026-08-15 · 仓库归档 `articles/2026-08-15-how-to-design-an-agent-harness/` · 抓取 2026-09-10（近两日 digests 未深写）

**原文关键段落**
> A better model fixes none of it. All of that lives in the software wrapped around the model: what it gets told, what it keeps, what it's allowed to touch, and who checks the result. That wrapper is the harness. You already have one. The only question is whether anyone designed it. … Write your stopping rule in one sentence, before you start. "Done means the test suite passes and the app boots." Not "done means the agent says it's done," which is what you have right now by default. … if it isn't in a file, it doesn't exist. … The agent that wrote the code is the worst available judge of whether the code works.

**翻译**
> 换更好的模型解决不了这些。问题都在模型外套的那层软件：告诉它什么、它记住什么、允许碰什么、谁验收结果。这层外套就是 harness。你已经有一个了——只是有没有人设计过它。……动手前先用一句话写停条件：「完成 = 测试通过且应用能启动。」不是「完成 = agent 说完成」——那是你现在的默认。……不在文件里，就不存在。……写代码的那个 agent，是判断代码是否可用的最差评委。

**问题背景**  
「说做完但没跑测试 / 二十分钟后忘规则 / 每会话重打三遍指令 / 走不开放心」——全是 harness 欠账。作者用 DoorDash 平台型、OpenAI 仓库型、Anthropic 三角色拆分三个真实形态说明：箱子外一半是你的。

**核心论点与论证脉络**
六项决策，每项「是什么 / 怎么做 / 何时跳过」：
1. **Loop 与停点**：停条件、坏结局策略、硬上限（轮次/墙钟）、无人值守必须落盘日志。引用：约 50 个公开 loop 里仅 74% 写明完成定义、仅 32% 跨跑记忆。  
2. **可见工具菜单**：按需加载（150k→2k token 量级）、结构化错误、砍冷门工具。  
3. **记忆窗口**：别塞满；按阶段换干净窗口；**规则要钉死**（不可被 summarization 冲掉）。  
4. **崩溃存活**：SPEC / PLAN / PROGRESS / DECISIONS（+ 可选功能清单 JSON）；每成功一步 commit。  
5. **触达边界**：OS 级目录与网络代理；别迷信点点点审批（93% 一律点过）；短寿命凭证。  
6. **谁判完成**：独立会话验收、真跑真点、失败案例做 eval、最差三次取劣、盯「流畅辩解」型假成功。

**方法/架构要点**
- 周末最小集：≤100 行说明书当目录、两次踩坑变 linter、四文件 + commit、钉死规则、20 任务×3 跑取最差。  
- 成本诚实：Anthropic 有 harness 的长跑可比无 harness 贵 20×+——只对「否则交不出手」的工作划算。

**可落地启示**
- 今天下午就能做：写一句 `done_when` + 建四文件。  
- 审批提示若总是点过，换成边界，而不是再加一句「请小心」。  
- 「agent 开始一味附和」= 会话该重启的信号。

**与其他层关系**  
相对昨日 Field Guide 的七层/六桶：本文更像 **施工清单**（决策顺序与跳过条件）。Loop 停条件、独立 verifier、证据门直接接到 loop/graph 的 gate；权限与工具网关是 harness 核心。

**评价/局限**  
密度高、可执行；部分统计（政策违反率、审批点击率）来自单点研究/厂商自述，宜当数量级提示。未展开多 agent 图拓扑——作者刻意停在「先能离开房间」。

## 3. Harness · 学科综述：从「选模型」到「设计环境」

**标题：** Harness Engineering: The Engineering Discipline Behind Reliable AI Agents  
**作者/来源：** Vinayak G Hejib · DEV Community  
**链接：** https://dev.to/vnayak_hejib/harness-engineering-the-engineering-discipline-behind-reliable-ai-agents-kap  
**时间：** 发表 2026-09-03 · 抓取 2026-09-10

**原文关键段落**
> How do we build a system that allows a probabilistic model to do reliable engineering work? … Agent = Model + Harness … The model may be the most intelligent component in the system, but it isn't necessarily the component that determines system reliability. … Better model → More capable agent → More ambitious tasks → New failure modes → Better harness … Don't just fix the failure. Improve the environment that allowed the failure to happen. … When generation becomes extremely cheap, verification becomes one of the scarce resources.

**翻译**
> 我们如何建一套系统，让概率模型去做可靠的工程工作？……Agent = 模型 + Harness……模型可能是系统里最聪明的部件，却未必是决定可靠性的那一块。……更好的模型 → 更能干的 agent → 更野心勃勃的任务 → 新的失败模式 → 更好的 harness……别只修这一次失败，要改进允许失败发生的环境。……当生成变得极便宜，验证就成了稀缺资源。

**问题背景**  
Agent 已能改仓、跑命令、开浏览器、干几小时；瓶颈从「选哪个模型」换成「如何让概率部件在确定性流程里可控」。

**核心论点与论证脉络**
1. **谱系**：Prompt → Context → Harness（环境问题）。  
2. **模型变强不会消灭 harness**：能力边界外扩 → 新失败 → harness 进化（可删旧脚手架，但整体不消亡）。  
3. **十七个工程命题**浓缩为可操作面：上下文是有限注意力；仓库要 **agent-legible**；工具是受控执行接口；权限是宪章；query loop 是心跳；失败是主路径；恢复要保动量；验证须独立；多 agent 是不确定性分区而非堆人；feedforward+feedback；架构可执行化；**harnessability** 成为架构质量；人上移抽象；吞吐改变经济学；熵需要垃圾回收环；最高杠杆是 harness 改进环；终局是 harness/meta-harness 自改进。  
4. 文末 checklist：信息 / 工具 / 状态 / 验证 / 恢复 / 治理 / 演化七组问题——比「先选模型」更正确的开工顺序。

**方法/架构要点**
- Feedforward（规则、docs、skills）+ Feedback（测试、lint、eval agent）。  
- 重复口头纠正 → 应变为测试/linter/skill/工具/规则（一次交互 vs 永久杠杆）。  
- 引用 OpenAI Codex 内部实验、Anthropic 长跑 artifact、Martin Fowler ambient affordances 等，把散点收成一张学科地图。

**可落地启示**
- 排障话术：先问「缺能力 / 不可见 / 不可执行」，再改 prompt。  
- 把「harnessability」写进架构评审：边界清晰、可测、可发现、可强制。  
- 高吞吐下优先加自动化反馈，而不是线性加人审。

**与其他层关系**  
几乎全写 harness，但明确 loop（heartbeat、恢复、验证环）与多 agent 分区（靠近 graph）。与 Yarchi 的六决策互补：本文给世界观与清单，Yarchi 给周末可落地顺序。与 DAIR「Harness Engineering」论文合集（YC Paper Club）同周舆论场。

**评价/局限**  
适合对齐团队语言与优先级；实现代码少，需回到 OpenAI/Anthropic 原文与源码论文取证。末段 meta-evolution 偏前瞻，生产要慎用无人门控的自改 harness。

## 4. Loop · 五件套 + 一根脊骨：设计替你去 prompt 的系统

**标题：** Loop Engineering  
**作者/来源：** Addy Osmani · O’Reilly Radar（转自作者博客）  
**链接：** https://www.oreilly.com/radar/loop-engineering/  
**时间：** 2026-06-22 · 抓取 2026-09-10（近两日 digests 未覆盖这篇奠基文）

**原文关键段落**
> Loop engineering is replacing yourself as the person who prompts the agent. You design the system that does it instead. … Loop engineering sits one floor above the harness. The harness … runs on a timer, it spawns little helpers, and it feeds itself. … A loop needs five things and then one place to remember stuff. … `/goal` keeps going until a condition you wrote is actually true, and after every turn a separate small model checks whether you are done, so the agent that wrote the code isn't the one grading it. … Two people can build the exact same loop and get completely opposite results. One uses it to move faster on work they understand deeply. The other uses it to avoid understanding the work at all.

**翻译**
> Loop engineering 是把「亲自去 prompt agent」换成「设计替你去 prompt 的系统」。……它在 harness 上一层：harness 被定时器驱动、拉起小帮手、自我投喂。……一个 loop 需要五样东西，外加一处记事的地方。……`/goal` 一直跑到你写的条件为真；每轮结束后由另一个小模型判是否完成——写代码的那个不给自己打分。……两个人可以建出一模一样的 loop 却得到相反结果：一个用它加速自己真正懂的工作，另一个用它逃避理解。

**问题背景**  
Peter Steinberger / Boris Cherny 的口号落地后，需要一张「跨 Codex 与 Claude Code 同构」的能力表，并说清 loop 仍加剧的三类债。

**核心论点与论证脉络**
| 原语 | 在 loop 里的工作 | Codex / Claude Code 映射（文中） |
|---|---|---|
| Automations | 定时发现与分流 | Automations 页 / cron·`/loop`·hooks·GHA |
| Worktrees | 并行隔离 | 内置 worktree / `--worktree`·`isolation: worktree` |
| Skills | 外置项目意图 | 双方 `SKILL.md` |
| Plugins & connectors | 接到真实工具（MCP） | Connectors + plugins |
| Subagents | maker ≠ checker | TOML agents / `.claude/agents` |
| State spine | 跨会话记进度 | Markdown / Linear 等 |

典型形状：早班 automation 调 triage skill → 写入状态板 → 每项开 worktree → 实现子 agent + 评审子 agent → connector 开 PR/更新票 → 难项进人工 triage。

**方法/架构要点**
- `/goal` = 可验证停条件 + 独立判分模型（maker/checker 应用到停步本身）。  
- Skill 防「意图债务」；worktree 防文件撞车，但人审带宽仍是并行上限。  
- 三件不会被 loop 删掉的事：验证仍在你、理解会腐烂、舒适姿势可能是认知投降。

**可落地启示**
- 先画五原语缺哪块，再谈「全自动」。  
- 停条件写成机器可检；判完的模型不要是干活的那个。  
- 建 loop 的目标应是「加速你懂的工作」，不是「合法化你不看 diff」。

**与其他层关系**  
作者明确：**loop 在 harness 上一层**。相对昨日 LangChain 四环：本文更偏「产品内原语对照表」与人因风险。相对 Hanako：Hanako 教节点内 loop / 图间边；Addy 教外环调度与跨工具同构。

**评价/局限**  
跨工具对照极清晰，是 loop 入门首选；日期较早（6 月），未纳入 8–9 月源码级 harness 论文细节。对 token 成本持保留态度——富裕与拮据用户体验会分叉。
